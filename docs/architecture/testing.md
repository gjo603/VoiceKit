## The runner

**Run the test suite** (2026-08-01 — one command, both languages):

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tests\Run-Tests.ps1
```

The runner first **load-checks the shipped entry points** (tracked `macros\*.ahk` via `git ls-files` — never the user's untracked macros — plus `VoiceKitLauncher.ahk`, `lib\LoopRunner.ahk`, `lib\Watchdog.ahk`, `mcp\uia_probe.ahk`, the complete templates, and `VoiceKit.ahk` in a temp copy with an EMPTY module index so user modules can't decide the verdict), each `/validate` bounded at 30 s and tree-killed on timeout (a `#Warn` dialog would otherwise wedge it). Every macro includes `_Common.ahk`, so this is what catches a new library function clashing with a name some macro already uses. Then it executes every `tests\*-selftest.ahk` (skipping `*-target.ahk` helpers), then `mcp\test_conformance.py` — with `mcp\.venv`'s Python when that exists, so the fastmcp wire tests run instead of skipping — and exits nonzero on any failure. ## Conventions, and what each one cost

Conventions the runner depends on — keep them when adding a suite: no framework, but one shared include — **`tests\_harness.ahk`** (`TestBegin(name)`, the retrying `Emit`/`Say`, `Check`, `TestEnd()`, and for target-driven suites `TargetLaunch`/`TargetState`/`TargetStop`) and **`tests\_target.ahk`** for the target helpers (`TargetServe(suite, stateFn, gui)`: publish, stop-file, 120 s self-exit); both are named so the runner's globs never execute them, and both stay ASCII. Each `<name>-selftest.ahk` writes PASS/FAIL lines to `<name>.result` beside itself, ending with `ALL PASSED` / `N FAILURE(S)`. **The result file is the verdict, never the process exit** — a bad vtable offset can hang rather than crash, and a step failure's MsgBox blocks forever; both must read as failures, not wedge the runner (it kills a test at 120 s and reaps leftover `*-target*` processes). Tests drive their own throwaway windows/processes, never the user's apps or the resident master, and their scratch output (`tests\*.result` / `.state` / `.stop`) is gitignored. `tests\` is dev-only: it's on the installer's drop list and never ships. Runner scripts stay **ASCII-only** — PowerShell 5.1 reads a BOM-less UTF-8 file as ANSI, and a mojibaked em-dash inside a string can break parsing. Two more conventions, both paid for in phantom failures (2026-08-01): (1) **result-file writes RETRY** (`Emit`/`Say` in `_harness.ahk`) and the runner polls with `FileShare.ReadWrite` — a plain `Get-Content` poll denies writers, and a colliding bare `FileAppend` in a test THROWS, popping a dialog that reads as a 120 s timeout blamed on an innocent suite (measured: 11.7k of 20k appends failed against a `Get-Content` loop); (2) **a test pins its target window to the PID it just launched** (`TargetLaunch` in `_harness.ahk`: `Run(..., &pid)` + `WinWait("Title ahk_pid " pid)`) — a leftover target from an earlier run can donate its window to a bare `WinWait` for the instant before the fresh target's `#SingleInstance Force` kills it, leaving the captured hwnd pointing at a window that dies mid-test (measured: 5 of 6 rapid re-runs). A third (2026-09-30): (3) **a test never raises a real toast** — Windows keeps a toast on screen for as long as the desktop is idle and hands it the FOREGROUND when a window closes, after which no background process can activate anything; on an unattended run one suite's toast failed the next run's `browser-selftest`/`engine-vars-selftest` wholesale (it read as "fails on HEAD too"). Hiding the tray icon does NOT pull a toast on Windows 11 (measured). Engine and loop notifications go through `WfTray` in `Workflow.ahk`; a harness that reaches them sets `wfTrayOff := true` and can assert on `wfTrayLast` instead.

## End-to-end engine tests

**Test the workflow engine end-to-end** (the established pattern — no framework): write a throwaway `.steps.txt` plus a harness script that calls `RunWorkflow()` and writes PASS/FAIL to a result file, then run it with a timeout. A timeout with no result file almost always means a step failed and its error MsgBox is blocking. Target throwaway AHK GUI windows with unique titles (e.g. a button that writes a proof file when clicked) — never drive the user's real windows in tests. **One more timeout cause**: PowerShell's `Start-Process -Wait` waits on the whole process TREE — a harness that reloads the resident master (e.g. testing hotkeys) never "finishes" because the master is its child. Check for the result file instead of trusting the wait, and never kill such a wrapper's tree without restarting `VoiceKit.ahk` afterward.
