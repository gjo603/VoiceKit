# The workflow engine and the loop runner

> Moved verbatim from `CLAUDE.md` on 2026-09-30 (the rules stayed there; the
> history and design notes live here). "Above"/"below" may point into a sibling
> file — `CLAUDE.md`'s architecture index says which file holds which section,
> and "the traps section" / "the lockstep list" are in `CLAUDE.md` itself.

`lib\Workflow.ahk` (step format, run log/record, conditionals, waitfor, ask/collect/set and `{{Name}}`, the `fill` step, Acc→UIA lookup, pacing), `lib\Acc.ahk`, and `lib\WorkflowLoop.ahk` + `lib\LoopRunner.ahk`. The Studio bullet of the original list is in `studio-and-recorder.md`.

**The workflow subsystem** (one data format; engine + Acc + loop runner + builder):

- `lib\Workflow.ahk` — the engine. Parses and runs `workflows\<Base>.steps.txt`: one step per line, `type|paramA|paramB|paramC`, params percent-encoded (`WfEncode`/`WfDecode`; `%`, `|`, newlines). Step types: `run`, `focus` (activate-or-launch), `waitwin`, `wait`, `waitfor` (see below), `text`, `ask` (see below), `collect` (see below), `set` (see below), `capture` (see below), `fill` (see below), `keys`, `click`/`dblclick`/`rclick`/`hover` (element-name first via Acc, recorded window-relative coords as fallback in paramC — `hover` MouseMoves there and dwells ~700 ms so hover-triggered menus/tooltips appear), `drag` (2026-07-26: `drag|<window>||x1,y1,x2,y2` — paramB stays empty, both window-relative press/release points live in paramC; playback presses, travels in ~16 small MouseMove increments — apps ignore a teleporting SendMode-Input move — and releases; always positional, so it goes through `WfPosOnlySettle` like a position-only click and gets the ⚠ marker; `WfDragDesc` renders the path and, like `WfDurDesc`, must never throw), `move`, `close`, plus the **branching** trio `if`/`else`/`endif`. The loader pads short lines, so older 3-field files still work. A failing step stops the run with an always-on-top MsgBox naming the step. **Playback is patient by design** (recorded timing is coarse, and pre-2026-07-23 recordings captured none — see pause capture below): a `focus` with no launch command and the click steps `WinWait` up to 10 s for their window before failing — don't "optimize" that back to an instant `WinExist` check. Position-only clicks/hovers (no element name) additionally go through `WfPosOnlySettle` — WinWaitActive + `WaitForInputIdle` on the window's process + a 1200 ms settle — because they fire blind and can't retry while content renders the way `AccFindByName`'s 3 s budget lets named clicks (a bare 400 ms pause clicked into half-loaded windows). **Abort hook** (2026-07-24): the global `wfRunAbortCheck` (a callable, "" when unset) makes a run stoppable mid-flight — `WfAborted()` is polled between steps, and every long block is sliced to honor it: `WfSleep` (Wait steps + the 300/400/700/1200 ms settles), `WfWinWait` (the 10 s window waits), `WfPosOnlySettle`'s WinWaitActive/WaitForInputIdle loops, and the ask dialog's wait (an open ask dialog is destroyed on abort). An aborted run returns false **quietly** — the failure MsgBox is suppressed when `WfAborted()` (a stop mid-window-wait must not pop "Window not found"), and the final `return !WfAborted()` covers a stop during the last step. The 150 ms beats and `AccFindByName`'s 3 s budget stay plain (sub-perceptible / Acc.ahk untouched). `RunWorkflowLoop` installs the hook (`(*) => wfLoopStop`) and clears it on exit, so Stop Looping cuts in mid-pass; non-loop runs never set it and are unaffected. `text` and `keys` steps end with a 150 ms settle (matching ask/click) — recorded keystroke steps otherwise replay back-to-back within milliseconds and race the app's UI (`{Down}` into an autocomplete list that hasn't populated). `WfDurDesc` renders wait milliseconds human-readably ("2.6 s") and must never throw — WfDesc draws the error popup for the very step whose param may be junk.
  - **Run log and run record** (2026-08-01) — a run used to leave nothing behind but a modal popup, so a batch that died at step 7 was indistinguishable from one that worked, and the reason string built for the popup was thrown away. Two artifacts now, both under `logs\` (user data, gitignored): **`workflow-runs.log`** (one line per step, rolling — trimmed to the newest half at 1 MB, cut on a line boundary, written to a temp file and moved over the log so a kill mid-trim can't empty it) and **`workflow-runs.ini`** (the LAST run of each workflow, one section per workflow base, machine-readable — the MCP reports from it). Globals: `wfRunName` (the workflow's file base, set by `RunWorkflow`/`RunWorkflowLoop`/Studio's Test), `wfRunQuiet`, `wfLogFolder` (self-tests point it at `%TEMP%` so the suite never writes into the user's history — named `wfLogFolder`, not `wfLogDir`, because that would collide with `WfLogDir()` in AHK's shared namespace). **Every failing step funnels through `WfRunFail`**, which records + logs + reports and returns false; the quiet returns (`WfRunFinish("stopped"/"cancelled")`) cover abort and cancel, so `outcome` is one of ok/failed/stopped/cancelled/error and the three are never conflated. Two invariants: the record is written **before** the failure popup (a caller that gave up waiting can still see what happened while the dialog sits there), and steps are logged **as written**, never with `{{Name}}` resolved — the placeholder is the diagnostic part and an ask answer may be a password. `WfRunRecordUpdate` lets the loop add what only it knows (`passes_done`/`passes_total`) after the fact. The section is written **whole, in one `IniWrite(pairs, path, sect)`** (2026-09-30) — per-key writes never removed anything, so a plain run after a loop was reported with the old loop's start time and pass counts. A cancelled ask dialog in `RunWorkflow` records `cancelled` too. **Failure reasons are recorded as written too** (2026-09-30, WP9): a reason is built from the RESOLVED step (`Window not found: Smith John - Excel`), and the record and log travel (`run_automation` / `read_log` → MCP → a cloud model), so `WfRunFail` passes it through **`WfUnsubst(reason, s, sr)`** first — every field `{{Name}}` changed is put back to its as-written text in the reason (longest resolved text first, plus its `Trim()`med form, since several messages quote a trimmed name) → `Window not found: {{Client}} - Excel`. Generic on purpose: it covers every `WfRunFail` call site (window criteria, element names in click/hover/if/waitfor/collect, `Unexpected error:` texts) without each message having to know; the `run` and `fill` special cases (G2/G4) stay as the first line of defence. The local popup and the quiet-mode tray note keep the resolved reason — they're for the person at the machine. Limit: a value that reaches a reason in a transformed form (not as the verbatim field text) isn't caught. `engine-runlog-selftest` section 9 feeds a value through `askVals` (as a batch row does) and asserts neither the record nor the log carries it.
  - **Quiet mode** (`wfRunQuiet`, set by `RunWorkflowLoop` when it has a `batchFile`) — a headless batch replaces the failure popup with a TrayTip (every engine/loop TrayTip goes through `WfTray`, which self-tests silence with `wfTrayOff`) (the loop's completion prompt is gone for everyone now — see the loop bullet). This is not cosmetic: a modal blocks inside the loop process, so `proc.wait()` on the Python side only returned once a human dismissed it, which is half of why every batch reported "finished cleanly". A user-driven loop is unaffected and still gets its dialogs.
  - **Conditionals**: `RunWorkflowSteps` is an index/program-counter `while` loop (not a `for`-each), so an `if` whose condition is false can skip to its matching `else` (or past `endif`); `WfSkipToElseOrEndif`/`WfSkipToEndif` do depth-aware matching so blocks nest. An `if` step is `if|<window>|<element>|<condType>` — condType lives in **paramC** (like `click` keeps coords there), so the Studio's edA→paramA, edB→paramB field model is unchanged. `WfEvalCond` supports deterministic state tests only: `winexists`, `winnotexists`, `elementexists`, `elementnotexists`, plus `textvisible`/`textnotvisible` (2026-07-31 — a case-insensitive SUBSTRING search over the window, so you can react to what the app *says* when no element name is knowable: "No results found"). `clipboardchanged` is deliberately **rejected** by `WfEvalCond` — "changed" needs a before-value that a point-in-time `if` can't supply, so it is waitfor-only. Guardrails (from the production review): `WfEvalCond` rejects an **empty window** (else `WinExist("")` would match the last-found window and mis-branch); `WfElementPresent` uses a **short 700 ms Acc budget** (not the 3 s click-path budget) since a condition is a point-in-time snapshot — the long budget stalled every absent-element check, badly inside a loop. `else`/`endif` are param-less markers; unknown condType stops the run like a failed step. Balance is enforced at authoring time, not run time: Studio `BlockBalanceError` (and the MCP writer) refuse to save/test/create unbalanced `if`/`else`/`endif` — an unbalanced block would otherwise *silently truncate* the run while Test falsely reports success. Backward compatible: workflows with no `if` run identically (every step is a normal step).
  - **Event waits / `waitfor`** (2026-07-31) — `waitfor|<window>|<element or text>|<condType>[,<seconds>]` blocks until the named thing is actually true, then continues **immediately**, and on timeout fails with a message saying *what never happened*. It replaces hand-tuned `wait` milliseconds, which are a bet on how slow the machine is that morning, and closes the "typed into the void" hole: a workflow can now detect that a search matched nothing *before* acting on it. **It reuses `WfEvalCond` wholesale**, so the `if` vocabulary and the wait vocabulary can never drift — anything testable is waitable. Design notes: seconds live in **paramC beside the condType** (`WfWaitParts` splits them) because paramC is already the comma-delimited "typed extra" slot (click coords, drag paths) and the format is fixed at 4 fields; junk/negative seconds fall back to 10 rather than failing the step. `clipboardchanged` is handled *inside* `WfWaitFor`, not `WfEvalCond`, because it is the one condition with memory (baseline = the clipboard when the step began). Polling is `WfSleep(150)`, so **Stop Looping cuts a wait short** like every other long block; an abort returns an error string that `RunWorkflowSteps` suppresses, exactly as a `WfWinWait` timeout does. `waitfor` deliberately does **not** activate its window — it only observes (unlike `waitwin`, which activates). `WfTextVisible` tries `WinGetText` first (one cheap call, catches classic Win32 captions — **visible controls only**, via `DetectHiddenText(false)`, restored after: apps pre-create hidden "No results" statics) before `AccTextPresent`, a new Acc.ahk tree walk with the same limits as `AccNodeOnce` (depth 14, 6000 nodes, deadline) so a browser's huge tree can't stall a run. **Known semantics worth remembering**: `elementexists` means "in the accessibility tree with a non-empty rect", which does *not* track a control's `.Visible` — measured: a hidden AHK Gui control still reports a location. Apps that hide rather than destroy will keep reporting the element present; the click path is unchanged deliberately, since adding a visibility test there could regress recorded workflows.
  - **Ask-for-input** (2026-07-23): `ask|<label>|<suggested answer>|` collects a text value from the user and types it (SendText) at the step's position. **All asks are gathered UP FRONT**: `RunWorkflowSteps` calls `WfGatherInputs` before step 1 — one plain always-on-top dialog (`WfAskInputDialog`, native controls so Voice Access can click OK/Cancel; deliberately not themed — the engine keeps no Theme dependency) per **unique label** (case-insensitive; a repeated label is asked once, typed at every spot). Cancelling any dialog aborts the run **quietly** (returns false, no error popup). Asks inside an if-branch are still asked (branch outcomes aren't knowable up front — documented behavior). `RunWorkflowSteps(steps, askVals := "")` accepts a pre-filled Map to skip the dialogs — that's how the loop runner feeds batched rows. The `ask` case is handled inline in `RunWorkflowSteps` (like `if`/`else`/`endif`), NOT in `WfRunStep`. Blank labels fall back to "Input" via `WfAskLabel`, but every authoring surface (Studio dialog, MCP writer, ParseDraft) requires one.
  - **Collect / data collection** (2026-07-24): `collect|<label>|<element name>|` is ask's mirror — it GRABS a value at its position and saves it under the label. Empty element = **copy the current selection** (`WfCopySelection`: `^c` through `ClipCapture` in the self-contained `lib\Clip.ahk` — clipboard restored in a `finally`, 1 s wait; nothing-copied is a step failure with a friendly message. `AIGrabInput` and the Browser.ahk copy helpers share the same helper). Non-empty = **read that named box's accessible value** in the active window via **`WfFieldValue`** (2026-09-30 — it was `AccValueByName` alone, so a collect inside a web page always failed): the same interleaved MSAA→UIA lookup as a click, 3 s total. MSAA goes first every round and a value it finds wins, so desktop workflows read the box they always did (Acc.ahk grew `AccValue` + a node-returning `AccNodeOnce`; it PREFERS a same-named element with a non-empty value because oleacc gives a label and its box the same name — the label's empty value must not win). The UIA half (`WfUiaFieldValue`, one look per round) asks for the **Edit** of that name (`UiaFindEdit` — a plain find returns the label that shares its name) and reads it with `UiaValueOnly(el, &has)`, never the Name (which would hand back the needle); with no such Edit, any same-named element that HAS a ValuePattern counts (combo, spinner), one without (a label, a button) does not. Found-but-empty in either tree is a legitimate empty box, but only at the deadline — until then it keeps looking in case the box fills in late; not found at all is a step failure whose reason names the box, never a value. Handled inline in `RunWorkflowSteps` (like `ask`), which takes a third param `collected` (a caseless Map the values land in; "" = discard). **Where values go**: the workflow's sheet, via `WfSheetApplyResults(sheetPath, askLabels, colLabels, results)` — each result `{src, ins, out}`: `src > 1` fills the collect columns of that sheet record **only if it still holds the inputs that produced the result** (else the unclaimed row that does, else a new row — a sheet edited mid-run must not send results into someone else's row) (loop batches fed BY the sheet — `WfLoopCsvRows` tags each row Map with a `srcRec` *property*, and the chooser marks `plan.fromSheet`), `src = 0` appends a row of inputs-used + values-collected (single runs via `RunWorkflow`, which now pre-gathers inputs itself so it can save them; ask-each loop passes, imported/typed batches, input-less loops). Input columns precede collect columns; extra user columns/cells are preserved; a locked sheet (open in Excel — Excel locks CSVs) falls back to appending `<Base>.results.csv`, and nothing is ever overwritten that couldn't be read first. The CSV core (`WfCsvParse`, `WfCsvField`, `WfSheetWrite` — UTF-8 BOM + CRLF) moved INTO Workflow.ahk from WorkflowLoop.ahk so stubs get it. Studio **Test** passes a map and shows the values in a popup but never writes the sheet. `.inputs.csv`/`.results.csv` are delete artifacts (AHK `DeleteWorkflowArtifacts` + MCP delete). **Collected cells are formula-escaped** (2026-09-30, `WfSheetSafeCell`): a non-numeric collected value starting with `=` `+` `-` `@` is written with a leading `'` so a scraped `=HYPERLINK(...)` can't become a live formula in Excel; numbers (`-12.50`, `-$1,234.56`) and the user's own input cells are written as-is. `read_workflow_sheet` returns the stored text, apostrophe included.
  - **Named values / `{{Name}}`** (2026-07-31) — every `ask` label, `collect` label and `set` name is a value the rest of the run can reuse by writing `{{Name}}`. Before this, an ask answer was typed at exactly one position and the clipboard was the only carrier, so using one value twice meant manual round trips. **No format change**: still `type|a|b|c`, and an **unknown name is left literal**, so every workflow written before this behaves identically (and a typo shows on screen instead of typing nothing). New step `set|<name>|<value>|` names a value outright; its value is itself substituted, so values compose (`set|Greeting|Hi {{First}}|`). Built-in fallbacks `{{clipboard}}`, `{{date}}`, `{{time}}`, `{{datetime}}` — **fallbacks, not reserved**, so a user label named "Date" still wins and no label is off-limits. Implementation: `WfSubst` + **`WfSubstStep`**, which resolves into a *copy* of the step immediately before dispatch — so `WfRunStep` needed **no changes at all**. Substituted: `text`/`keys`/`run` paramA, window criteria (paramA of focus/waitwin/click/dblclick/rclick/hover/drag/move/close/if/fill), element names (paramB of click/dblclick/rclick/hover/if/collect) and a fill's label, `set`'s value, `fill`'s value (**paramC — the first and only substituted paramC**, 2026-09-30), and `capture`'s command (paramB; the `run` target and the capture command substitute in command-line mode — see the selection bullet). **Not** substituted: `wait` ms, paramC everywhere except `fill`'s value (coordinates, condTypes, a capture's timeout), `move` positions, and an `ask` label/suggestion (asks are gathered before step 1, so nothing would resolve). `WfStepSubstText` mirrors that field list for the authoring-time check and must be kept in step with `WfSubstStep`. The namespace is seeded from `askVals`, which is why **batches get it free** — loop rows and MCP `run_workflow_batch` rows arrive as that same Map. `collect` writes to both `collected` (sheet) and the namespace; **`set` values are run-local and never become sheet columns**. Failure popups use `WfStepDesc`, showing the step as written plus its resolved form when they differ — otherwise an error just says `{{Customer}}` and hides what was tried. `RunWorkflowSteps` takes an optional 4th arg `varsOut` (pass a Map to watch values fill in; it IS the working namespace, so it survives a failed step — that's how Studio Test lists every value). Authoring aids: `WfVarNames` feeds the Add-dialog hint listing what you can type, and `WfUndefinedVars` powers a **warning, never a block** on Test/Save (a `set` inside an if-branch is legitimate). Caveat to keep in mind: in a **`keys`** step a substituted value is inserted into a `Send` string, so `{ ! ^ + #` are interpreted — `text` is literal and is the right step for arbitrary values.
  - **The File Explorer selection — `{{selected_file}}` / `{{selected_files}}`** (2026-09-30, roadmap WP2+WP3+WP5) — the "select a client's invoice in Explorer, say *open Extract Invoice*" case. Two more built-in fallbacks in `WfBuiltinVar` (a user label of the same name still wins): the singular is ONE full path, unquoted; the plural is every path in double quotes, space-joined (a Windows path can't contain `"`, so the quoting is exact) — the command-line form. **Never a guess**: a workflow that uses the singular refuses to start unless exactly one item is selected ("Select exactly one file in File Explorer first — found N"), and the plural refuses with none. Both read one **snapshot**, the global `wfSelection` (`""` = not taken, else an Array), taken by `WfSelectionPrecheck` only when `WfSelectionNeeds` finds a step using one of the names (scanning `WfStepSubstText`, so exactly the substituted fields count; a name the workflow defines itself doesn't) — Explorer's COM is never touched otherwise, and `WfBuiltinVar` only READS the snapshot, so the authoring check (`WfUndefinedVars`) stays COM-free. It is taken **before the ask dialogs and before any step** (a `run|C:\folder` step would change which Explorer window is topmost): `RunWorkflow` checks before gathering inputs, `RunWorkflowSteps` right after `WfRunBegin` (reusing a host's snapshot), a loop once before its chooser for all passes (`RunWorkflowLoop` keeps a pre-pinned one — it is always a fresh process), and Studio Test clears it before each test. A refusal is recorded as outcome **`error`** with the reason (no path in it) and reported through `WfSelectionReport` — a popup, or a tray note under `wfRunQuiet`; a loop refuses through `WfLoopEarlyError`. **Arguments are the selection**: `RunWorkflow` (the stub entry point only — LoopRunner's arguments mean something else) turns the stub's `A_Args` into `wfSelection` (full paths via `WfFullPath`), so MCP `run_automation(args=[...])` — or a file dropped on the workflow's shortcut — tests a selected-file workflow on a fixture with Explorer never consulted, and the generated stub text is unchanged. Steps are still logged as written, so a client path never reaches the run log or record. The lookup itself is `lib\ExplorerSel.ahk` (`ExplorerSelectedFiles(hwnd := 0)` → Array, `ExplorerFolderPath`), `#Include`d by `Workflow.ahk` and Split Pages: the **active tab** of the topmost Explorer window with a selection (Windows 11 tabs share one HWND — see the traps in `CLAUDE.md`), file-system items only (a file inside a `.zip`, "This PC" etc. are skipped), `[]` on any failure. Verified on Windows 11 25H2 against throwaway windows by `tests\explorer-selftest.ahk`; the no-tabs (Windows 10) path is by reasoning only (one Shell entry per window = unambiguous), and desktop icons are deliberately unsupported. Explicitly not built: a newline-joined variant, one-loop-pass-per-file, an `if` on selection state, and a generic dry-run. **In a command line the selection is always quoted** (2026-09-30, with `capture`): `WfSubst(text, vars, cmdLine := true)` — used for `capture` paramB and `run` paramA — follows cmd's own quote parity: OUTSIDE a quoted argument (an even number of `"` so far) `{{selected_file}}` is emitted as `"<path>"`; INSIDE one the author opened it goes in bare, because their quotes already cover it — so `python invoice.py {{selected_file}}`, `python invoice.py "{{selected_file}}"` and `python invoice.py "--in={{selected_file}}"` are all one correct argument, spaces and `&` included (review fix: the first cut only absorbed quotes that *hugged* the placeholder, which broke the `"--in=..."` form). The plural hugged by the author's quotes absorbs them, since several paths can't share one pair. Chosen over "document that authors must quote it" because that rule fails silently on exactly the first file with a space; chosen over "always quoted everywhere" because a `text`/`set` value that types a path must not grow quotes. Only the two selection names get this — any other value in a command is inserted as-is (quote `"{{Customer}}"` yourself), and a user value that shadows the name is never touched. A `run|{{selected_file}}` still opens the file (Run takes the quoted form).
  - **The `capture` step** (2026-09-30, roadmap WP4) — `capture|<name>|<command line>|<seconds>`: run a command hidden, keep its stdout as `{{name}}`. With the selection names it makes "select an invoice, say *open Extract Invoice*" about five steps (capture → focus → text `{{Invoice Data}}` → keys). Handled inline in `RunWorkflowSteps` like `set` (it writes the namespace; `WfRunStep` knows nothing about values); the value is **run-local** — never a sheet column (`WfCollectLabels` is untouched). paramA = the name (never substituted), paramB = the command (substituted in command-line mode), paramC = timeout seconds (`WfCaptureSecs`: a positive number, anything else → 30; never substituted). `WfVarNames` lists the name, so later `{{name}}` isn't flagged and the Add dialog offers it. `WfCapture(command, secs)` → `{ok, value, reason, errTail, aborted, code}`, never throws. How it runs, and why: **a nested cmd, fed through an environment variable** — `cmd /d /v:on /s /c "chcp 65001 >nul & cmd /d /s /c "!VK_CAPTURE_CMD!" 0<nul 1>"!VK_CAPTURE_OUT!" 2>"!VK_CAPTURE_ERR!""`. **stdin is NUL** (review fix): the console is hidden, so nobody could ever answer a prompt — `set /p`, Python's `input()`, `pause` used to sit until the timeout (measured: 4 s of a 4 s limit); now they read end-of-input at once. The outer cmd owns the redirects and never parses the user's command (delayed expansion substitutes it after parsing), so nothing in the command can escape the redirects, and the inner cmd has full cmd semantics (`&`, `|`, quotes, `%VAR%`) and starts AFTER `chcp 65001` — a cmd reads its code page once at startup, so a chcp in the same instance left its own `echo` output in the OEM code page (measured: `café` came back as `caf\x82`). `PYTHONIOENCODING=utf-8` covers Python (it ignores the console code page when redirected). The env vars are set on the AHK process and restored in `finally`. stdout and stderr go to **separate** temp files (`%TEMP%\vk-capture-<pid>-<tick>-<seq>.out/.err` — a stderr warning can't end up in the value, the Split Pages `2>&1` bug), deleted in `finally` with a short retry (`WfDeleteSoon` — a just-killed child can hold its redirect handles for a moment; measured on the abort path). Working directory = `WfRootDir()` (the folder holding `lib\` — the install root on an installed copy), whatever launched the run: a stub runs in `macros\`, a loop in the root, and a relative path must mean one thing. **Timeout and Stop**: `RunWait`'s pid is filled in as the process starts and a `SetTimer` closure sees it while RunWait waits (measured), so a 100 ms watcher kills the WHOLE tree with `taskkill /T /F` on the deadline or `WfAborted()` (killing cmd alone would orphan the python under it); an abort ends the run quietly as `stopped`. Output: over 1 MB (`WfCaptureCap`) fails rather than truncating (a half-read extraction is worse than none); otherwise decoded by `WfDecodeBytes` — UTF-8 (BOM skipped) when valid (`MultiByteToWideChar` with `MB_ERR_INVALID_CHARS`), else CP0 — CRLF→LF, trailing whitespace trimmed, leading kept; an empty value with exit 0 is legitimate. A command over 8,000 chars fails before running (cmd's limit is 8191 — reachable with a big `{{selected_files}}`). **Failure hygiene** (a user decision): a nonzero exit fails the step with reason `Command exited with code N.` — no stderr, no resolved command — because the reason goes to `workflow-runs.log`/`.ini` and from there into MCP responses, and a traceback or a filled-in `{{selected_file}}` names a client's file. The last ~10 stderr lines (`WfCaptureTail`, read from the file's end) reach only the local failure popup, through `WfRunFail`'s new `detail` parameter (never recorded, logged, or put in the quiet-mode tray note). The step itself is recorded as written (placeholder, not value) like every step. The same hygiene now covers a failing **`run`** step (review fix): its reason used to be `Couldn't open: <resolved target>`, which with `run|{{selected_file}}` put the client's path in the record — `RunWorkflowSteps` now records the target as written when it held a value (the popup's step line still shows what was tried). A deliberate nonzero-OK is the author's `& exit /b 0`. **Trust**: this is the first step that executes something, so a shared or downloaded `.steps.txt` now carries code — the README says to share such workflows like scripts, the Studio shows the command in the step list (`WfDesc`), and an ask answer substituted into a command is a command-injection route (quote it; `%` still expands inside quotes). Draft With AI refuses `capture` by name (`ParseDraftInner`), and its prompt says never to emit one. Not built: an ignore-exit-code flag, the exit code as a value, `if` on a captured value, env-var handoff of the selection, `run_workflow_batch(files=...)`. Tests: `tests\engine-capture-selftest.ahk` (its child is `engine-capture-selftest-target.ahk`) and conformance's STEPS fixture + guards + the args→`{{selected_file}}`→capture→later-step round trip in `test_run_automation_passes_args_and_cwd`.
  - **Filling a box by its label / `fill`** (2026-09-30, roadmap WP8 — from an office typing invoice figures into a web-based form app's input screens, where an agent had been reduced to a Ctrl+F trick) — `fill|<window>|<label>[#N]|<value>` puts a value into an input found by its label and **proves it took**. Clicking a box and typing was always possible; knowing it worked was not — a missed click, a pop-up that took the focus, a box that trimmed the value all looked like success. `WfFill` in order: (1) **find** — `WfFillFind`, 3 s interleaved budget, abort-aware: UIA first, **input kinds only** (`WfFillUiaInputs`: Edit, ComboBox — an editable combo's own inner Edit is the same box and is not counted twice — and Spinner), never the Text label sharing the name (the label-vs-input trap) and **never Document**: a browser page's root is a Document named after the page, so a label matching the title would select-all the whole page. MSAA is the fallback for desktop inputs only it exposes (`AccInputNodes` in `Acc.ahk`: role editable-text / combo / spin button, in tree order, same depth/node/deadline limits as `AccNodeOnce`). **Occurrence**: `"Amount#2"` = the 2nd input with that label in tree order, `"##"` = a literal `#` (`WfFillLabel`; an odd run of `#` before trailing digits ends in the separator, `#0` is refused, and a single `#` anywhere else is literal). Several matches and no `#N`: the **first** is filled and the run log gets a note (`N inputs are labelled "X" — filled the FIRST…`), never the value; too few for the `#N` asked: `Only N inputs are labelled…`. A same-named label/button with no box behind it: `…something there IS named that, but it isn't a box you can type into`. (2) **disabled** → refused before anything is typed. (3) **click for real** (`UiaClickEl`, jittered like any element click, with its scroll-into-view rescue); only when there is nowhere to click is the value set through ValuePattern (`UiaSetValue`) — a rescue, logged, because a set skips the app's own keyboard/validation handlers. (4) **focus gate** (`WfFillFocusGate`, polled ≤1 s): the focused element must BE the box or sit inside it (up to 3 ancestors — a combo's inner edit), compared with `UiaSameElement` (CompareElements); otherwise nothing is typed and the step fails. A readback alone can pass while the text landed in a different box — measured once (`lib\Browser.ahk` `BrowserTypeVerified`). The MSAA half gates on `STATE_SYSTEM_FOCUSED` or the thread's focus HWND (`GetGUIThreadInfo`) being the node's window or its child — the window test only for a node that IS its own window (child id 0 and a window rect within 8 px of the node's, `WfWinRectNear`), because a simple or windowless element shares its host's window with every sibling box and "the focus is in that window" would let the gate pass while the typing went next door (review fix). (5) `^a`, `SendText` (or `{Delete}` for `""`, which clears the box), default SendLevel. **No `{Esc}`** — it reverts an in-progress edit in some apps and closes dialogs in others; Chrome's autofill drop-down doesn't take the keyboard focus, so it can't eat the typing, and if a pop-up ever does the gate refuses (the fix is a `keys|{Esc}` step before the fill). (6) **readback** (`WfFillVerify`, retried ≤1 s so a box that reformats as you type can settle): `UiaValueOnly(&has)`, or select-all + copy through `ClipCapture` (clipboard restored) for a box with no ValuePattern — only after the gate proved the focus is on it; `AccValue` on the MSAA path. A copy that lands nothing is retried with the rest and ends as "couldn't read it back" rather than a mismatch — except when clearing, where an empty box copies nothing too. **Password boxes** (`UiaIsPassword`, slot 35 — verified in `uia-selftest`; `STATE_SYSTEM_PROTECTED` over MSAA) are filled, never read back, and the log says so. **`WfFillMatches`** is deterministic and never accepts a different digit sequence: identical or equal after trim, case-insensitively; both numbers once `$€£¥`, spaces, a trailing `%` and **properly grouped** thousands commas are dropped (`1,234,567` — a comma anywhere else, `1,5` or `12,34`, makes it not-a-number, so a decimal comma typed into a box that kept `15` can't pass as the same digits), equal after dropping **trailing** decimal zeros only (`1234.5` = `1,234.50` = `$1,234.50`; `(12)` and `12-` are −12; `1.5` ≠ `15` and **`01234` ≠ `1234`** — leading zeros stay, a ZIP or EIN that lost one changed); or a mask that only added/dropped `- space ( ) / _` with no `.` or `,` on either side (`123456789` = `123-45-6789`). A value with a line break is refused at run time and at every authoring surface (`SendText` turns it into Enter, which submits a web form). **Privacy**: no failure reason and no log note ever contains the value — the reason names the box by its **as-written** label and window (`WfFill`'s `shownWin`/`shownLabel`, like `run`'s target), and typed-vs-held goes only to the local popup via `WfRunFail`'s `detail`; steps are logged as written, so a batch's `{{SSN}}` stays a placeholder (a value typed literally into a step is part of the workflow, like a Type text step's). A browser gets the one-look MSAA pacing (`WfIsBrowserWindow`). `RunWorkflowSteps` runs `fill` inline (for the detail and the notes); `WfRunStep`'s `fill` case serves direct callers. `wfFillUiaOff` is a **self-test-only** switch that skips the UIA half, because Win32 controls show up in both trees and no ordinary box is MSAA-only. **Fill values declare inputs** (`WfFillInputNames`): a `{{Name}}` in a fill VALUE that no ask/collect/set/capture defines and no built-in covers is an input of the workflow — `WfAskLabels` lists it after the ask labels, so a single run asks for it up front (`WfGatherInputs`), the loop's sheet gets a column for it, and a batch must answer it (Python mirror `_input_labels`, pinned by `test_fill_inputs_match_the_engine`); `WfUndefinedVars` stops warning about it. Without that, a batch could reach fill steps only through `ask` steps, and an ask TYPES its answer at its own position. The Studio's Add dialog has the step ("Fill in a box by its label"), and its Pick element now falls back to UIA so it can read a web input's name; for a fill it writes the picked name with every `#` doubled, since `Unit #2` would otherwise mean "the 2nd box labelled Unit". Tested by `tests\engine-fill-selftest.ahk` against a separate target process (`docs\architecture\testing.md`).
  - **Finding an element: MSAA first, UIA second** (2026-08-01) — `Acc.ahk` was the engine's only pair of eyes, which stopped working: current Chrome exposes **no web page content over MSAA at all**, only its own toolbars and tabs (measured — an MSAA dump of a data-rich Chrome window gave ~109 descendants, all browser chrome; the same window over UIA gave the whole page). Every named click or read inside a page failed, *including saved workflows that used to work*. **`WfFindElement(win, name)`** now backs the `click`/`dblclick`/`rclick`/`hover` cases (and `WfElementPresent`/`WfTextVisible` for `if`/`waitfor`), trying both trees. Three design points worth keeping: (1) **Acc goes first** — recorded desktop workflows were built against the names oleacc reports and must keep matching them. (2) The two are **interleaved in short 400 ms passes**, not run back to back: a straight "3 s of Acc then 3 s of UIA" would make every browser click pay three seconds of futile MSAA walking before it could succeed, and would double the wait before a genuinely missing element is reported — alternating keeps the total at the 3 s it always was. Condition checks (`WfElementPresent`, `WfTextVisible`) **split** their short 700 ms budget rather than doubling it, so a point-in-time check stays a snapshot. `WfElementPresent` (2026-09-30) does ONE look per tree per round plus a 150 ms pause — only presence matters there, so order can't change the answer, and browsers no longer pay ~0.5 s of futile MSAA retries per check. `WfFindElement` deliberately **keeps** its 400 ms MSAA head start: there the winner is the element that gets clicked, and cutting it would let UIA answer first for a late-rendering desktop control (e.g. match the title bar's "Close"). **Browsers get a shorter MSAA turn** (2026-09-30, `WfIsBrowserWindow`: root window class `Chrome_WidgetWin_1` — Chrome, Edge and Electron apps — or `MozillaWindowClass`): one MSAA walk per round instead of the 400 ms retry turn, in `WfFindElement` and `WfFieldValue`. Chromium's MSAA tree is only its own chrome, drawn before the page, so the retries were pure delay — measured against the pretend browser in `engine-hybrid-selftest-target.ahk`, a UIA-only button went from ~580 ms to ~45 ms, while a desktop window's timing (and which element it matches) is untouched. MSAA still goes first every round; the one change is that an element rendering during what used to be MSAA's retry sleep may now be answered by UIA first — acceptable in a browser, deliberately not done for desktop windows. Needles are **trimmed** before either tree is asked (MSAA's walk always trimmed; UIA's exact-match condition did not). (3) `WfUiaRect` falls past a match with a **zero rect** to the other matches, because a zero rect is both "collapsed/offscreen" and how the label-vs-input trap shows up. **No format change**: the same steps files run, and `tests\engine-hybrid-selftest.ahk` proves the fallback fires by finding a caption button ("Minimize") that lives in the non-client area the engine's `OBJID_CLIENT` walk cannot reach — the Chrome problem's shape, reproduced without a browser.
  - **Pacing and aim** (2026-08-01) — a `wait` step may be a **range**, `wait|600-1400`, which pauses `Random(600, 1400)`; and a **named-element** click lands a few pixels off centre. Both exist because a workflow looped against a website with metronome timing and pixel-identical clicks is the cheapest bot signal there is. Neither makes a run non-deterministic in any way that matters — the same steps run in the same order. Details that matter: `WfWaitMs` is the one parser (Studio, `ParseDraft` and the MCP guard all defer to it or mirror it), a backwards range is read the way it was obviously meant, and junk is still rejected rather than guessed at. Jitter is **clamped to a third of the rect** in each direction (`UiaJitteredCenter` in `UIA.ahk` is the one copy of that maths — `WfClickPoint` and `UiaClickEl` both call it; `WfJitter` survives as an alias of `UiaJitter`), so however large the setting, a jittered click cannot leave the element it was aimed at; **position-only clicks, drags and hovers stay exact** — coordinates are what they're for, and a hover aimed at a menu strip wants the centre. The switch is `logs\settings.ini` `[Workflow] ClickJitter` (pixels, default 3, `0` = off), surfaced as the Studio's fifth checkbox, and overridable per process with the `wfClickJitterPx` global (which is how the self-tests assert exact centres). It is `wfClickJitterPx`, **not** `wfClickJitter` — that would collide with `WfClickJitter()` in AHK's shared namespace.
- `lib\Acc.ahk` — minimal MSAA (oleacc) wrapper used for click-by-name. Still the engine's FIRST lookup; `lib\UIA.ahk` is its fallback (above). See the traps below before touching it.
- `lib\WorkflowLoop.ahk` + `lib\LoopRunner.ahk` — the **loop** feature. `RunWorkflowLoop(stepsFile, phrase)` (in WorkflowLoop.ahk) re-runs a workflow's steps until stopped, showing a themed always-on-top **Stop Looping** bar (bottom-left, work-area anchored), pausing `delayMs` (default 1500) between passes via an interruptible `WfLoopSleep`, and **stopping automatically if a step fails** (so a broken workflow can't spin). Stop = the voice-clickable button, or `Ctrl+Alt+Shift+X` (`WfLoopRequestStop` sets the `wfLoopStop` global) — and it's **immediate**: the loop installs the engine's `wfRunAbortCheck` hook (see the engine bullet), so a stop cuts in mid-pass, inside Wait steps and window-waits, with no failure popup. `LoopRunner.ahk` is the entry script the `loop <name>` shortcut targets — it reads the workflow base from `A_Args[1]`, resolves the steps file, and calls `RunWorkflowLoop`; `#SingleInstance Force` means only one loop runs at a time. **`RunWorkflowLoop` returns its outcome string and `LoopRunner` exits with a matching code** (0 ok / 1 failed / 2 stopped-or-cancelled / 3 never-ran): it used to `ExitApp()` unconditionally, so the MCP's only success signal was an exit code that was always 0 — every batch reported "Finished cleanly", including the ones that failed partway and collected nothing. The exit code is the coarse signal; `logs\workflow-runs.ini` is the detailed one. WorkflowLoop.ahk `#Include`s Workflow.ahk + Theme.ahk itself (LoopRunner adds only `_Common.ahk`); it is **not** included by normal workflow stubs, so the engine keeps no Theme dependency. The stop hotkey reuses `Ctrl+Alt+Shift+X` (Studio's stop-recording key) — safe because looping and recording aren't concurrent; if both ever were, only one process wins the global-hotkey registration and the Stop button still works. **Batched loop inputs** (2026-07-23): if the workflow has `ask` steps, `RunWorkflowLoop` first shows `WfLoopInputPlan`, which leads with the workflow's **inputs sheet** — `workflows\<Base>.inputs.csv`, created on demand (`WfSheetWrite(path, [labels])`: header-only, one column per label, UTF-8 BOM + CRLF for Excel; `WfCsvField` does RFC-4180 quoting) and opened via file association with a Notepad fallback; **Run from my sheet** re-reads it every time, a watcher timer (mtime+size stamp, fully try-guarded — it can fire between Destroy and the post-Show wait) refreshes the row count and moves the `Default` accent between the two sheet buttons, and the delete flows remove the sheet with the workflow (`DeleteWorkflowArtifacts` + MCP `delete_automation`). The dialog also sets the **pause between passes** (a seconds box; every start funnels through one `Start()` that validates it and persists per workflow to `logs\settings.ini` `[Loop] <Base>`; input-less loops keep the 1500 ms default and still start with no dialog). The other routes remain: import any **CSV** (picker), **type rows in** (`WfLoopTypeRows`, one edit per label + Add Row), or **ask each pass** — sheet and import share one validator, `WfLoopCsvRows` (header row must name every label case-insensitively, extra columns ignored, `WfCsvParse` is a real RFC-4180 parser: quoted fields may hold commas/doubled quotes/newlines; it now lives in Workflow.ahk). A batch runs one pass per row (`RunWorkflowSteps(steps, row, collected)` — no dialogs), shows "row i/n" on the bar, stops by itself after the last row, and reports completion; cancel aborts before the bar ever shows. **Collect write-back**: ask-each passes gather via `WfGatherInputs` in the LOOP (not the engine) so inputs can be saved beside results; each completed pass with collects pushes `{src, ins, out}` and the loop saves them all once at the end via `WfSheetApplyResults` (partial batches — stopped or failed midway — still save the completed rows; a failed save TrayTips the error). **Results survive a loop that never reaches that save** (2026-09-30): each such pass is also appended to a journal, `logs\loop-journal\<Base>.<stamp>-<pid>.jnl` (`WfLoopJournal*`, fields `WfEncode`d), an `OnExit` handler saves (and records `stopped`) on a polite exit such as a replacing `#SingleInstance Force` launch, and `WfLoopSaveResults` merges journals left by **dead** loops of the same workflow into the next save — a journal is deleted only once its rows landed in the sheet or `.results.csv`. **Newer results win**: the usual recovery is re-running from the sheet, so a leftover and this run often cover the same row — row-filling results go to `WfSheetApplyResults` newest first, leftovers are flagged `old`, and an `old` result whose row a newer one already filled is dropped (counted in `skipped`), never appended (an appended duplicate input row would run twice on the next sheet run). `WfSheetWrite` writes a temp file and moves it over the sheet, so a process killed mid-save (the `OnExit` save runs while a Force replacement waits to terminate it) leaves the old sheet whole. Workflow deletes remove them (`DeleteWorkflowArtifacts` + MCP `delete_automation`). **Early errors never pop a modal in a headless batch** (`WfLoopEarlyError`: record first, then TrayTip under `wfRunQuiet`, MsgBox otherwise). **A finished loop reports on the tray, never with a dialog** (2026-08-01): the "Done — ran … for all N rows" box and the YesNo "Open it now?" offer are both gone, for user-driven loops as well as headless batches. They said nothing the run record (`logs\workflow-runs.ini`) and the saved sheet don't already hold, and a modal at the end of a run is one more thing to dismiss — `wfRunQuiet` no longer branches here at all. `WfLoopOpenFile` stays: the chooser's sheet-edit button still uses it. **Headless batch** (2026-07-24): `RunWorkflowLoop(..., batchFile)` skips the chooser — the CSV is the batch, delay = the workflow's remembered pause, Stop bar still up; `LoopRunner.ahk <Base> <batch.csv>` is the entry (the MCP's `run_workflow_batch` writes a per-run `logs\mcp-batch-<stamp>-<pid>.csv` and launches it; passing the sheet itself as batchFile sets fromSheet so results fill in place). Since 2026-09-30 (WP7) that batch file may come from **any CSV or Excel range** — `run_workflow_batch(source=...)` normalizes it in Python, so this path is unchanged: the file still has a header naming every ask label, plus one extra column, `VoiceKit source row`, which `WfLoopCsvRows` ignores as an unknown header but which keeps every record non-blank, so no row Python kept is dropped here and pass N stays the Nth row written. Python does all the skipping (blank / required / already-done rows) before writing. A non-sheet source takes the ordinary `src = 0` route — results append to the inputs sheet as new rows; the source file is never written. `mcp\_conformance\batchrows.ahk` feeds such a file to the real `WfLoopCsvRows` in `test_batch_source_file_round_trips_through_real_wflooprows`.
