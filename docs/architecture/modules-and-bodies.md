# Modules, bodies, keys and companions

> Moved verbatim from `CLAUDE.md` on 2026-09-30 (the rules stayed there; the
> history and design notes live here). "Above"/"below" may point into a sibling
> file — `CLAUDE.md`'s architecture index says which file holds which section,
> and "the traps section" / "the lockstep list" are in `CLAUDE.md` itself.

The two trigger paths, the per-user registry files, isolated module bodies and their status/stop channel, the replace semantics, companion hotkeys and key choice.

**Two trigger paths** (see README for the user-facing story):

1. **Launch macros** — standalone scripts in `macros\`, each with a shortcut in Start Menu → `Voice Macros`. Voice Access natively opens Start Menu entries, so "open \<name\>" works with zero Voice Access config. This is why saving anything voice-triggerable means creating a `.lnk` there.
2. **Bridge hotkeys** — modules in `hotkeys\` bind `Ctrl+Alt+Shift+<key>`; the user manually pairs a Voice Access shortcut to that key combo (no API exists to do it programmatically — hard platform limit). `bridge-map.txt` is the registry of used keys and the user's recreate list. `_index.ahk` is the include manifest; `VoiceKit.ahk` (resident, tray icon) loads it. Both are per-user files made from shipped defaults (see "Per-user files" below). Reserved keys, excluded from the allocator pool (`BridgeKeyPool()` in `_Common.ahk`, mirrored by the writer's `BRIDGE_POOL`): **E, N, R** (master's own), **X** (Workflow Studio's stop-recording / loop-stop hotkey), **H** (Workflow Studio's mark-hover hotkey while recording — `^!+h` records a `hover` step at the mouse), **I** (its mark-ask-input hotkey while recording — `^!+i` opens a label dialog and records an `ask` step), and **C** (its mark-collect hotkey while recording — `^!+c` records a `collect` step for the current selection).

**Per-user files** (2026-09-30) — `hotkeys\_index.ahk` (the include manifest), `bridge-map.txt` (the key registry and recreate list) and `hotkeys\Snippets.ahk` are both what VoiceKit ships and what every create/delete rewrites, so tracking them kept personal wiring one `git commit -a` from the remote, a build from the working tree shipped `#Include`s for modules it didn't contain, and an upgrade couldn't add a shipped hotkey without overwriting the user's copy (the RecordMySteps `^!+W` companion never reached upgraded installs — logged 2026-07-27). Now git tracks **`hotkeys\_index.default.ahk`, `bridge-map.default.txt`, `hotkeys\Snippets.default.ahk`**; the live files are gitignored and never shipped. **`SeedUserFiles(root)`** (`lib\_Common.ahk`; the first step of `MasterPreflight`, so the launcher, every reload and the MCP's preflight run it, and `VoiceKit.ahk` runs it on start too) creates a missing live file as a byte copy of its default, then **merges** any shipped `_index` include / bridge-map record the live file lacks, appended in the file's own line-ending style. Rules the merge must keep: keyed by the module **file** (a companion the user moved to another key is present); a **commented-out** copy counts as present (never resurrect what the user parked); a shipped line whose module file doesn't exist is skipped (a removed companion stays removed — until an upgrade reinstalls its file); a shipped record whose key is already taken (the raw-scan `BridgeFreeKeys` rule) is held back **with its include**, since two `^!+<k>` definitions stop the master loading; `Snippets.ahk` is **seeded only, never merged** (a snippet deleted in Home must stay deleted). Python mirrors it exactly — `voicekit_writer.seed_user_files` in `master_preflight`, and the path accessors `_hotkeys_index` / `_bridge_map_file` / `_snippets_file` seed a missing file on first use so an MCP call on a fresh clone works; `test_seed_user_files_matches_ahk` runs both implementations case by case. Listings skip the `*.default.ahk` files (`list_automations`; AHK lists modules from the map). The former samples (ToggleTimer, MeetingNotes, MorningTabs, WorkLayout, CleanScreenshots, OpenPublicUserFolder) live in `templates\examples\` now; an older install's live copies stay where they were, gitignored.

**Isolated module bodies** (2026-07-31) — custom hotkey code no longer lives in the master. `hotkeys\<Base>.ahk` is a key binding that launches **`hotkeys\bodies\<Base>.body.ahk`** in its own process (same shape as the companion modules), so a hard crash there ends one short-lived process instead of the layer. Helpers: `HotkeyBodyRel`/`HotkeyBodyFile`/`HotkeyLauncherContent`/`HotkeyBodyContent`/`HotkeyIsolatedCreate` in `_Common.ahk`, mirrored by `BODY_SUBDIR`/`_body_rel`/`_hotkey_launcher_content`/`_hotkey_body_content` in `voicekit_writer.py`. The **launcher** is load-checked before wiring because it's the half the master includes; MCP `create_hotkey_module` load-checks the **body** too (2026-09-30, rolled back with the launcher on failure) — not to protect the master (a bad body can only hurt itself) but to tell the caller now, instead of a load-error dialog on the first key press in a process nobody watches. The GUI's `HotkeyIsolatedCreate` stays launcher-only: it only ever writes the placeholder body. Scope is deliberate: the **no-code** generators (Open Something / Type Text) stay in-process — one `Run()`/`SendText()` line can't crash, and a process launch would only add latency. MCP `create_hotkey_module(isolate=True)` is the default; `isolate=False` writes the old in-process form for modules that must keep state between presses (a toggle whose variable has to survive). Delete parity: Home's Delete and MCP `delete_automation` both remove the body; Home's Edit opens the **body**, and so does the scaffolder's custom-code Notepad hand-off. `hotkeys/bodies/*.ahk` is gitignored like the rest of the user's modules. Existing modules are untouched — no migration. **One instance per body** (2026-08-03, from a real duplicate-scraper report): `#SingleInstance` compares hidden-window titles, and a starting script only creates that window once it has finished loading — so **two launches inside that gap both pass the check** (measured: two no-gap launches of a `#SingleInstance Ignore` script both survived; the other suspects were cleared — replacing the file mid-run and a message-blocked instance were both still detected). Generated bodies therefore also call **`BodySingleInstance(base)`** (`_Common.ahk`) right after the include: a kernel mutex (`Local\VoiceKitBody_<Base>`) claimed atomically, so the second process always sees it; the loser exits 0 quietly like Ignore, the handle is deliberately held for the life of the process, and a CreateMutex failure never blocks legitimate work. The directive stays too (belt for hand-written bodies). Existing bodies can add the one-line call themselves; `test_body_single_instance_mutex` proves the mutex alone (directive off) stops a duplicate against real processes.

**Body status** (2026-08-01) — a module body runs in its own process and can run for hours (a queue of a few hundred items is a real case), and its only way to say where it had got to was its own ToolTip: invisible unless you're at the machine, and gone the moment the run ends. So a body had no way to answer "is it still going, and how far in?" — the question the master's heartbeat file already answers for the layer itself. Same shape, one file per body: **`logs\body-status-<Base>.txt`**, a single overwritten line `<A_Now stamp>|<text>`. Write side `BodyStatus(base, text)` / `BodyStatusDone(base, text)` in `_Common.ahk` (every call try-wrapped — a status write must never be what stops the work it reports on); read side `BodyStatusRead` there and `voicekit_writer.body_status` in Python, guarded by `mcp\_conformance\bodystatus.ahk` + `test_body_status_reads_back_what_ahk_wrote` because it is another AHK-writes/Python-reads seam. Surfaced in **two** places: the home window puts the latest line on the module's row with how long ago it was written (a body that died leaves a line that simply stops getting newer), and `list_automations` carries it as `status` on the hotkey-module entry. **Cooperative stop** (2026-08-03) — the channel's other half: MCP `stop_module` drops `logs\body-stop-<Base>.txt`-style flag (`body-stop-<Base>.flag`, write side `_body_stop_file` in Python, read side `BodyStopFile`/`BodyStopRequested` in `_Common.ahk` — same name derivation, or a graceful stop can never happen), waits its grace period (0–60 s, default 5) for the body to exit, then `TerminateProcess`es what's left, scoped to the module's own PIDs — a pid it may not end (e.g. a body running elevated) is reported as `stopped: false` + `still_running`, never as stopped. `BodyStopRequested` **consumes the flag on sight** (one request stops one run) and `stop_module` removes it in every path, so a stale flag can never kill the next press; a body that never checks is simply force-killed after the grace — opt-in, no worse than before. `list_running` is the matching view: every executing body (matched on our interpreter + the `\hotkeys\bodies\*.body.ahk` path shape under THIS tree's `REPO_ROOT` — a body from another VoiceKit copy is never listed or stopped — never a loose substring; the anchor is the resolved path, so every launch site must spell it canonically — a junction/subst drive, 8.3 short name or `lib\..\` form would read as "not running") with pid, start time and its latest status line. Generated body headers document the check (both `HotkeyBodyContent` and `_hotkey_body_content` — keep the two mirrored); existing bodies are untouched. `test_list_running_and_stop_module` proves both paths against real processes. **Generated bodies now `#Include` `_Common.ahk`** and carry a commented `BodyStatus(...)` example in their header — a format change mirrored in `voicekit_writer._hotkey_body_content`. Existing bodies are untouched and can add the include themselves.

**Modules are replaceable** (2026-07-31) — `create_hotkey_module` on an existing name **replaces it in place** instead of erroring, matching `create_workflow`. The old asymmetry (workflows overwrite, modules refuse) forced delete-then-recreate, which cost more than inventing a new name and produced real name sprawl. Rules the replace path must keep: it **reuses the registered bridge key** (the Voice Access pairing is manual and there is no API to recreate it, so reallocating would silently break the user's voice trigger); it appends **no duplicate** `_index.ahk` / `bridge-map.txt` line (it checks `index_modules()` and the map, so an orphaned module missing one of them is repaired rather than doubled); it **un-quarantines** a parked `#Include` via `_uncomment_include` — re-creating a module that got parked for not loading *is* the "I fixed it" signal; it **rolls back** to the exact previous bytes if the generated launcher fails its load check; and it keeps an unwanted overwrite undoable — but **without echoing the old code** (2026-08-02): a replace banks the overwritten file in `logs\module-backups\<Base>.prev.ahk` (one per module, one step deep, written only on a replace that *succeeded*, removed by delete) and returns `previous_body_sha256` / `previous_body_length` / `previous_body_first_lines` / `previous_body_backup` instead of the full text, which used to cost a real session the old body's length on every one of five rewrites — the single largest token sink measured. `read_hotkey_module(name, previous=True)` returns the banked version through the MCP surface (an MCP-only client has no filesystem access, so the response fields alone would have quietly killed the undo promise); `update_ai_prompt` still echoes its short previous prompt, deliberately. `read_hotkey_module` is otherwise the matching read half — for an isolated module it returns the *body*, so an agent can edit rather than rewrite from memory. One reserved name: **`Snippets`** (`RESERVED_MODULE_BASES`), because `hotkeys\Snippets.ahk` holds every snippet the user owns and `clean_phrase("Snippets")` reaches it. `_index` needs no guard — `clean_phrase` strips the underscore, so that base is unreachable; don't "helpfully" add it back. The **GUI is deliberately unchanged**: New Automation → Always-On Hotkey still refuses a duplicate name (you're creating a *new* thing there), and Home's Edit button is the GUI's replace path.

**Companion hotkeys** (2026-07-15: "also press Ctrl+Alt+Shift+\<key\>" for when voice is unavailable) — Home's **Hotkey** button gives any workflow / macro / AI action / tool a keyboard trigger (snippets are typed already; hotkey modules already have one). The helpers live in `lib\_Common.ahk`: `HotkeyCompanionCreate` writes `hotkeys\<Base>.hotkey.ahk` — **the `.hotkey.` filename suffix IS the marker** (safe: scaffolded names come from `CleanPhrase`, which strips dots) — generated self-contained (no `_Common` calls, missing-target TrayTip guard, runs `macros\<Base>.ahk` via `A_AhkPath`) so it standalone-`/validate`s, and the create **load-checks it BEFORE wiring** `_index.ahk` + `bridge-map.txt` (a broken module would take every hotkey down on reload); the caller reloads the master. Giving an automation a different key is a replace inside `HotkeyCompanionCreate` (2026-09-30): the new module is checked in a scratch file first and only then is the old key retired, so a failed change really does leave the old key working (Home used to remove the old one first). Keys come from the same pool as the bridge allocator — `BridgeKeyPool()`/`BridgeFreeKeys()` in `_Common.ahk` are the AHK source of truth (the writer's `BRIDGE_POOL` mirrors it, and `test_conformance` byte-compares the two so they can't drift; "is this key taken" is ONE rule on both sides (2026-09-30 — the old two disagreed and could hand a key out twice): a key is used if the raw text holds `Ctrl+Alt+Shift+<k>|` anywhere (caseless) OR any line, **commented-out lines included**, has a trimmed first field of `Ctrl+Alt+Shift+<k>` (so a hand-padded line counts). AHK `BridgeFreeKeys` and Python `_used_bridge_keys` (allocator, `get_bridge_map` free list, a `key=` request) implement it identically, and `test_used_bridge_keys_match_ahk` runs both on one tricky map; the reserved letters are `RESERVED_BRIDGE_KEYS`).

**Choosing a key** (2026-07-31) — the pool is iterated one **character** at a time and now ends with punctuation: `[];',./-=\`. Every symbol was *measured* usable, not assumed — a generated module using it loads, `Hotkey()` registers `^!+<k>`, and a synthesized `Send "^!+<k>"` at SendLevel 1 actually fires it (the real question being whether Ctrl+Alt+Shift+`[` arrives as `{`). Deliberately excluded: `"` (breaks the string literals the generators emit), backtick (AHK's escape char), `|` (bridge-map delimiter), and Space/Enter (they register but a synthesized press never fires them). Punctuation sits **after** the letters and digits so auto-allocation still hands out a letter first and the symbols stay free for someone who asks. Asking is now possible on both sides: MCP `create_hotkey_module(key=...)` (via `normalize_bridge_key`, which tolerates `"Ctrl+Alt+Shift+["` and lowercase, and refuses a taken key by name), and New Automation's Always-On Hotkey dialog, which offers the free list in a dropdown instead of assigning one silently. `AllocateBridgeKey` in NewAutomation.ahk is **gone** — the dropdown replaced it, and dead code claiming to mirror the Python allocator is a drift hazard. A **replace keeps its existing key**; asking for a different one is refused rather than silently stranding the hand-made Voice Access pairing. The convention has one owner per side: AHK `HotkeyCompanionRel`/`HotkeyCompanionParent`, Python `COMPANION_SUFFIX` + `_companion_rel`/`_companion_parent`; registry writes/reads go through `BridgeRegisterModule`/`BridgeMapEntries` (NewAutomation registers through it too; the writer mirrors with `get_bridge_map`). **Listings fold companions into their automation's row** (Home's Hotkey column; `list_automations`' `hotkey` field) — a companion line needs no Voice Access recreation (the map header + README say so) and must never appear as a hotkey row of its own; orphaned companions (automation deleted behind our back) surface in Home as deletable "(missing)" Hotkey rows. **Delete parity, three places**: Home's Delete, Studio's `DeleteWorkflow`, and MCP `delete_automation` (workflow/ai_action/launch_macro) all retire the companion — the AHK GUIs share `DeleteWorkflowArtifacts` (the whole five-artifact workflow-delete recipe) and `HotkeyCompanionRetire` (remove + reload-if-existed) in `_Common.ahk`. One exception: a legacy workflow saved under a **tool's** name keeps the tool's companion — the companion is keyed by base, so retiring it would take the tool's shipped key (`RecordMySteps.hotkey.ahk`, ^!+W); the writer refuses a tool-named delete outright, before touching anything (`common-selftest` + `test_tool_named_workflow_delete_keeps_the_tools_companion`). MCP `press_hotkey` can press companions (they're registered combos); *creating* one via MCP is deliberately unimplemented — GUI-only for now.
