**`lib\UIA.ahk` — the UI Automation layer** (2026-08-01) — MSAA (`Acc.ahk`) is thin on modern apps (WinUI/XAML, WPF, Electron, browsers), whose UIA tree is complete where their MSAA tree is not. Reaching UIA from AHK means raw vtable `ComCall`s, and a wrong offset is an access violation, not a catchable error — that is what took the master down and prompted this. So the offsets are now written down, commented with the interface they belong to, and **all of them are exercised** by `tests\uia-selftest.ahk`. API: `UiaAvailable`, `UiaFromWindow`, `UiaFromPoint`, `UiaFocused`, `UiaFind` (by Name), `UiaFindById` (by AutomationId — prefer it, a developer sets it so it survives relabelling/translation), `UiaWaitFor`, `UiaName`/`UiaValue`/`UiaRect`/`UiaEnabled`/`UiaAutomationId`/`UiaControlType`, `UiaIsPassword` and `UiaSameElement` (2026-09-30, for the engine's `fill` step: a password box is never read back, and the focus gate asks whether the focused element IS the box it clicked — two finds of one control are two different wrapper objects, so only CompareElements can say), `UiaFocus`, `UiaInvoke` (InvokePattern, falling back to a click at the element's centre), `UiaSetValue` (ValuePattern — sets an edit outright, so nothing races the app's own handlers), `UiaClickName`, plus the structural walkers (2026-08-02): `UiaParent`/`UiaFirstChild`/`UiaNextSibling` (raw-view TreeWalker — RAW view deliberately, since Find* match the full tree and a control-view dump could hide the very element a find would return), `UiaControlTypeName` (readable names for the 50000-range ids), and `UiaDumpTree` (indented type-plus-name outline, bounded by depth, output lines AND the node budget). Verified offsets: **IUIAutomation** 3 CompareElements (2026-09-30), 6 ElementFromHandle, 7 ElementFromPoint, 8 GetFocusedElement, 16 get_RawViewWalker, 21 CreateTrueCondition, 23 CreatePropertyCondition, 25 CreateAndCondition; **IUIAutomationElement** 3 SetFocus, 5 FindFirst, 6 FindAll, 16 GetCurrentPattern, 20 get_CurrentProcessId (2026-10-14), 21 get_CurrentControlType, 23 get_CurrentName, 28 get_CurrentIsEnabled, 29 get_CurrentAutomationId, 35 get_CurrentIsPassword (2026-09-30, proved against a real ES_PASSWORD edit and a plain one), 38 get_CurrentIsOffscreen (2026-10-14), 43 get_CurrentBoundingRectangle (20 and 38 counted off `IUIAutomationElementVtbl` in `UIAutomationClient.h`, SDK 10.0.26100.0); **IUIAutomationElementArray** 3 get_Length, 4 GetElement; **IUIAutomationTreeWalker** 3 GetParentElement, 4 GetFirstChildElement, 6 GetNextSiblingElement; **InvokePattern** 3 Invoke; **ValuePattern** 3 SetValue, 4 get_CurrentValue; **ScrollItemPattern** 3 ScrollIntoView (2026-08-03); ScrollPattern (10004) is only ever *asked for* (GetCurrentPattern), never called — it is how `UiaIsScrollContainer` tells a clipping container (the same answer as `UIA_IsScrollPatternAvailablePropertyId` 30034). A VARIANT argument is passed **by reference** on x64 (24-byte buffer, `vt` at 0, value at 8) — the same trap as `Acc.ahk`'s `accLocation`; an int VARIANT is `vt` 3 / value at 8 (`UiaVarI4`). Everything returns `""`/`false` instead of throwing, so a module built on it can be wrong without being fatal.

**Finding the *right* element** (2026-08-01) — `FindFirst` by string property was not enough, because one accessible name routinely matches more than one element. Measured on a live registration form *and* reproduced in `tests\uia-selftest.ahk`: a `Text "Name:"` sits immediately above an `Edit "Name:"`, `UiaFind` returns the label, and because `UiaValue` falls back to the Name **nothing about the returned element says you got the wrong one**. Three ways out, all present: `UiaFindAll(hwnd, name)` (every match, tree order), an `occurrence` parameter on `UiaFind`/`UiaFindById`/`UiaFindOfType` (the Nth match — defaults to 1, so no existing caller changes), and int-property conditions — `UiaIntCondition` + `UiaAndCondition` build "Name = X AND ControlType = Edit", which is what **`UiaFindEdit`** (and the general `UiaFindOfType`) is. Prefer `UiaFindEdit` for form fields; `occurrence` is the escape hatch for everything else.

**Reading and clicking** — `UiaTextPresent(hwnd, needle, timeoutMs)` mirrors `AccTextPresent` (case-insensitive substring over Names *and* Values, retried), and `UiaDumpText(hwnd, maxChars)` returns the whole subtree's text newline-joined. They exist because capturing page text otherwise meant `^a`/`^c`, which depends on focus and stamps on the user's clipboard. Both read at most `UIA_NODE_BUDGET()` = 6000 elements — but the `FindAll` that produces them is ONE provider call nothing here can bound. `UiaTextPresent`'s deadline governs its **retries, not the scan** (2026-09-30): it used to break out of the scan at a deadline set *before* the `FindAll`, so on a big page it looked at one element and said "absent". Each attempt now scans the whole capped array (Name, then `UiaValueOnly` — no double Name read), so a `textvisible` check **can overrun its 350 ms snapshot budget on a large page** — a slower right answer beat a fast wrong one. **`UiaClickCenter(hwnd, name, timeoutMs, jitterPx)`** is the counterpart to `UiaClickName`: `UiaInvoke` fires InvokePattern, which is right for buttons and links (it works even when the control is scrolled away) but **wrong for a text field** — Invoke moves no mouse, focuses nothing, and plenty of `<input>`s expose no InvokePattern at all, so the call silently does nothing and the keystrokes after it land wherever focus happened to be. `UiaClickCenter`/`UiaClickEl` put the pointer on the element and click, restoring the caller's `CoordMode`. **Clicks fail loudly and rescue themselves** (2026-08-03, from a real session: a click on a virtualized web element "worked" — no error — and went nowhere, costing most of an hour): an element with no bounding rectangle is how offscreen/**virtualized** content presents (web pages realize only what's near the viewport — `UiaRect` returns an **object** `{x,y,w,h}` or `""`, never a string), so `UiaClickEl` first asks the element to **`UiaScrollIntoView`** (ScrollItemPattern; measured rescuing a scrolled-out Win32 list row) and re-reads the rect; if there is still nowhere to land it returns false with the reason in a new optional `&why` out-param, which `UiaClickCenter`/`UiaClickName`/`UiaInvoke` share (a find-miss `why` also warns about virtualization). All trailing-optional — no existing caller changes. The engine's click path is deliberately untouched: `WfUiaRect` keeps its own zero-rect skip, and auto-scrolling under a recorded workflow could change what a saved click does. (The `fill` step is the exception — `WfFillUia` clicks through `UiaClickEl` and so gets the 2026-10-14 visibility and hit-test checks below; the `click`/`dblclick`/`rclick` steps still click the centre of whatever rectangle `WfFindElement` returns.)

**An empty answer says why** (2026-10-12, from an agent automating a tax-software site in Chrome) — every find returned `""`/`[]` for "no match", "couldn't get the window root" and "the call threw and was swallowed" alike; one run's first `UiaFindAll` took 5 s and the next two came back empty in 0 ms, and the agent blamed a flaky browser when the page had simply changed. Every find now takes a trailing optional **`&why`** (positionally after the existing optionals, so no caller changed): `UiaFromWindow`, `UiaFindFirst`, `UiaFindElements`, `UiaFindCond`, `UiaFindAllCond` and the wrappers `UiaFind`/`UiaFindById`/`UiaFindBy`/`UiaFindAll`/`UiaFindEdit`/`UiaFindOfType`/`UiaWaitFor`. `""` on success; otherwise one of: UIA unavailable, `no window (hwnd 0)`, `no such window (hwnd N) — it has closed`, the own-process refusal, `couldn't get the window's UIA root element (ElementFromHandle failed: <message> (0xHRESULT))`, a missing condition, `the search failed: <error>` (never swallowed — `UiaErrText` adds the HRESULT and says what `UIA_E_ELEMENTNOTAVAILABLE` means), `only N matches, wanted occurrence K`, or `no match` — the retrying ones end with `after N ms (K attempts)`, so a 5 s miss and a 0 ms miss can't read alike. A failing call also re-fetches the window root before the next attempt (an error usually means the root went stale on navigation; a re-fetch that fails says the window is gone). `UiaClickName`/`UiaClickCenter` fold the find's reason into theirs: a plain miss keeps the virtualization advice, anything else says the *search* failed. Internals: `UiaFindFirstRaw` / `UiaFindAllRaw` are the bare FindFirst/FindAll with the error in `&err`; the window-level retry loops, `UiaTextPresent` and `UiaDumpText` use them.

**A scoped search can come back from outside its start element** (2026-10-12, same session) — in Chrome, `FindFirst` for an Edit started from three *different* label groups returned the *same* box all three times, an element outside every one of them; walking the tree level by level found the right ones. No error, a plausible answer. So `UiaFindFirst`, started below a window root, checks the hit with `UiaIsWithin(el, ancestor)` (raw-view parent walk + `CompareElements`, bounded) and, when it is outside, searches the start element's own subtree with **`UiaFindFirstWalk`** (pre-order over the raw walker, `UIA_NODE_BUDGET()` nodes, each node tested by FindFirst with TreeScope_Element *and* `UiaSameElement` so the test itself can't be fooled) and says so in `&why` — a non-empty `why` *with* an element is that note. `UiaFindElements` drops out-of-scope hits the same way (`UiaScopedHits`): it checks up to 32 evenly spaced hits, ends included, and only if one is outside checks every hit — a per-hit parent walk over a 6000-element answer would cost tens of thousands of cross-process calls. A start that is a window root (`UiaIsTopLevel`: its parent is the desktop, two hops) skips the check — everything in the window is in scope — and the retrying window-level finds don't pay even that. The decision is `UiaKeepInScope(hit, start, cond, scope, &why)`, separate so `tests\uia-selftest.ahk` can hand it an out-of-scope hit (the Win32 provider never produces one) as well as testing the containment helper both ways, a list-scoped search that must not return a same-named element outside the list, and the walk directly. Rule: search from the window root, or through these helpers — never a raw `ComCall(5/6)` from a sub-element.

**The tree dump says how complete it was** (2026-10-12, same session) — `dump_uia_tree` capped `max_depth` at 25, the site's inputs sat deeper, the outline showed the form as empty groups and a `name_filter` for a field's label came back with zero lines and no warning, which nearly read as "the field isn't there". `UiaDumpTree(hwnd, maxDepth, nameFilter, maxLines, &stats)` now reports `visited`, `cutAtDepth` (nodes at `maxDepth` that *have* children — subtrees not shown), `budgetHit`, `timeHit` (a 15 s `UIA_DUMP_TIME_MS()` cap, inside the probe's 25 s life, so a slow provider yields a partial report instead of a killed probe), `linesHit`, `why`, and a **`fingerprint`**: CRC-32 (ntdll `RtlComputeCrc32`, no AHK loop) over every visited node's depth, control type, name and automation id. The walk no longer stops at `maxLines` (it stops *printing*), so the counts and the fingerprint describe the whole walk and don't depend on `nameFilter` or `maxLines` — a filtered and an unfiltered dump of one unchanged page at one depth agree, and a changed page shows even when the window title didn't (the session's other trap). Only a walk that ended on its own is comparable: a `timeHit` walk gets **no** fingerprint (`""` — where a slow provider stops varies call to call, so two dumps of one unchanged page would differ and read as "the page changed"), and a `budgetHit` one covers only the first `UIA_NODE_BUDGET()` nodes (the note says so). The price of not stopping at `maxLines`: an unfiltered dump of a big page walks to the budget or the time cap — seconds, not the ~1 s of the old 300-node early stop; lower `maxDepth` for a quick look. `UiaTreeFingerprint(hwnd, maxDepth)` is the bare fingerprint for snippets (it passes `maxLines` 0 = collect no lines, so its `linesHit` stays false). `UiaFindFirstWalk` — `UiaFindFirst`'s fallback when the provider answers from outside the start element — is bounded by time as well as count (`UIA_WALK_TIME_MS()`, 5 s) and says "stopped after N nodes / T ms" when it gives up. The probe (`mcp\uia_probe.ahk`) writes these as header lines and errors with the `why` when nothing was visited; `voicekit_writer.dump_uia_tree` returns `nodes`/`cut_at_depth`/`budget_hit`/`fingerprint` (`time_hit` when set), raises the cap to `DUMP_MAX_DEPTH = 100`, and `_dump_note` says in plain words when subtrees were cut at `max_depth` ("N subtrees were cut off at max_depth=D — the match may be deeper; raise max_depth"), when the budget or time ran out, and — loudest — when a `name_filter` matched nothing in an *incomplete* walk; a filter that matched nothing in a *complete* walk says that too.

**A rectangle is not a place you can click** (2026-10-14, from an agent that built a ~1,500-line browser module against a live triage view in Chrome) — `UiaClickEl` only rescued an element with *no* rectangle. Chrome still reports rectangles for elements scrolled outside an inner scroll panel and for elements under a header pinned over the panel, so the click landed wherever that rectangle was — on a three-monitor desk, once a different monitor, which sent a download click somewhere else entirely. The reporter's two failed fixes are the spec for what not to do: intersecting **every** ancestor's box wipes the area out (web wrappers are often smaller than their content), and climbing to the desktop root and intersecting with it wipes out anything on a secondary monitor (the root's box is the *primary* monitor — measured here as well: `Pane "Desktop 1"` at 0,0, the primary's size). Now:
- **`UiaVisibleRect(el, &why)`** — the element's rectangle clipped by only what really clips: ancestors that are **scroll containers** (`UiaIsScrollContainer`, ScrollPattern), the element's **own top-level window** (`UiaClipChain`: the nearest ancestor that `UiaIsWindowRoot` — its `NativeWindowHandle` is its own GA_ROOT — so an owned dialog or dropdown ends at itself, not at its owner, which UIA lists it under (measured; code review 2026-10-14: the first version took "the ancestor below the desktop root" and clipped a dialog's controls to its owner's box). A walk that stops before reaching a window is a refusal, never read as complete, and the root is never intersected; `UiaVisibleRect`, `UiaHitCountsFor` and the dump's `UiaClipAbove` share that one chain, and `UiaClickablePoint` walks it once per click; `UIA_VIS_MAX_HOPS()` = 256 bounds it), and a **real monitor** (`UiaOnMonitors`: the largest piece on any monitor from `MonitorGet` — the virtual screen alone is not rectangular with mixed monitor sizes). `IsOffscreen` (`UiaIsOffscreen`, slot 38) is honoured too, but it is not enough on its own — measured: a Win32 button clipped entirely out of its scrolling parent pane keeps its rectangle and reports `IsOffscreen` false, which is exactly the Chrome-like case and what `tests\uia-selftest.ahk` uses as its stand-in. `why` says what kind of thing clipped it (`it lies outside the visible area of the scrolling container (a Pane) that holds it`, `it is not on any monitor …`); the optional `&detail` names it (`… container Pane "…"`).
- **`UiaElementAtPoint(x, y, &why)`** — `ElementFromPoint` (IUIAutomation slot 7, the POINT by value as one int64) with the own-process guard (`WindowFromPoint` + its process, refused before any UIA call) and a reason; `UiaFromPoint` is now a thin wrapper over it. **`UiaHitTest(el, x, y, &what, &detail)`** asks what is at the point and accepts `el`, anything inside it, or an ancestor **below `el`'s nearest scroll container / Document / top-level window** (`UiaHitCountsFor`) — Chrome answers with the nearest hit-testable ancestor, so some ancestors must count, but not one a click can land on without touching `el`. (Review, 2026-10-14: the first version accepted any ancestor but the desktop root; a header pinned over a panel is often a plain box the accessibility tree ignores, so a hit there answers with the panel or the page, and that click went ahead. Measured on Win32: a hit over a button, an edit, a static or a list-box row is the element itself, over a ListView row its own Text child — both inside `el`, so the narrower rule costs them nothing.) Anything else is in the way: `what` gives its control type (`a Text`, `a Window that holds the element …`, `… in another program`), `detail` names it (`UiaDescribe` + its window title, and the program when it is another process — `UiaProcessId`, slot 20). A window of *this* script at the point is reported as in the way from `WindowFromPoint` alone, never by asking UIA about it. x and y may be Floats (`r.x + r.w / 2` is one in v2, and the int64 packing threw on it — measured; `UiaPointArg` rounds).
- **`UiaClickablePoint(el, jitterPx, &why, &detail)`** is the whole decision, without clicking: visible rect (none → `UiaScrollIntoView`, wait up to 1.2 s, look again) → the jittered, clamped centre of the **visible part** (not the full rect; jitter stays inside it, so the determinism rule holds) → hit test (something in the way → one `ScrollIntoView` retry if not yet scrolled, then refuse; a hit test that is *unavailable* doesn't block). A refusal's `why` starts with one of three fixed phrases a caller may test — `no element`, `nowhere visible to click` (hidden / scrolled away / off-screen) or `something else is in the way` (covered). **`UiaClickEl(el, jitterPx, button, count, &why, &detail)`** is that plus the `MouseClick`, so `UiaInvoke`'s click fallback, `UiaClickCenter`, `UiaClickName` (all three gained a trailing `&detail` too), `lib\Browser.ahk` and the engine's `fill` step inherit it. It never clicks on a refusal. Measured cost on a shallow Win32 window: ~2 ms a click (a parent walk plus a hit test); a deep browser tree costs one parent step and one pattern query per level, twice when the hit is an ancestor.
- **`why` is safe to record; `detail` is not** (review, 2026-10-14). The engine's `fill` puts `UiaClickEl`'s `why` into the run's recorded failure reason, which is kept free of anything that can name a client — and another app's window title (a PDF's name, an email subject) or an element's name is exactly that. So the click path's `why` carries control types and coordinates only, and `&detail` — the same sentence with the names, window titles and program — is for a local popup, a module's own log or `Out()`.
- **Not purely a read, and dry runs refuse too.** The checks read the target, plus the deliberately live `ScrollIntoView` rescue (see "Dry runs" below), which really scrolls the target app; under a dry run a hidden or covered target is refused exactly as on a real run, where the old code logged a click at its rectangle.
- **One coordinate space** (review, 2026-10-14). Measured on this machine (one monitor, 150%): a UIA rectangle, `MonitorGet`, `WinGetPos`, `WindowFromPoint` and `MouseMove` **all follow the calling thread's DPI awareness** — a DPI-unaware thread saw a button at 247,270 200x60 that a per-monitor-aware one saw at 371,405 300x90 — and AutoHotkey runs system-aware (`GetThreadDpiAwarenessContext` → awareness 1), where Windows virtualizes all of them on a monitor whose scale differs from the main one: the reporter's desk. So every public function works in the caller's context (its numbers agree with the caller's own `MouseClick`/`MouseGetPos`), and `UiaClickEl` decides and clicks inside **`UiaDpiPhysical()` / `UiaDpiRestore(prev)`** (per-monitor-v2: physical pixels, nothing virtualized), restoring the script's context even on a refusal (the suite checks). Waits inside the scope use **`UiaSleep`**, which hands the thread back its own context for the Sleep, so a timer or hotkey that runs meanwhile doesn't inherit ours. A module clicking a point it computed itself wraps the decision and the click in the same scope. Still unmeasured: an actual mixed-scale desk (there isn't one here; on a single-scale desk system-aware and per-monitor numbers are identical, measured).
- Known gaps: the visible rect of a Win32 scroll container includes its scroll bars, so a centre can land on one — the hit test then refuses rather than clicks. Something `position: fixed` inside a scrolling panel isn't clipped by it on screen but is clipped here (a refusal with the reason, never a wrong click). With the narrower hit rule, a Chrome element whose hit test answers with the scroll panel or the Document itself (rather than the element or a wrapper below them) is refused — a false refusal, never a wrong click. Neither, nor Chrome's own behaviour (does every inner scroll panel expose ScrollPattern? does `ScrollIntoView` clear a pinned header? what does `ElementFromPoint` answer over a styled box?), nor a mixed-scale multi-monitor desk, could be measured here — the suite proves the logic on Win32 windows on one monitor plus one window moved off every monitor. The suite's fixtures: a scroll pane with a button inside, one two-thirds past its edge (clicked in its visible part) and one wholly past it (refused); a button under an overlay (refused, no click — every fixture counts its clicks and the mouse must not move); a window off every monitor; and a ListView showing five and a half rows with one overlay over its top row slot (a pinned header: refused "still, after ScrollIntoView") and one over the half row at the bottom (the hit test says "in the way", `ScrollIntoView` scrolls the row out from under it, and the retry clicks it — the list's own click count proves where it landed).

**Walking up, icon names, subtree dumps** (2026-10-14, same session) — **`UiaFindAncestorById(el, id, maxHops := 64, &why)`** / **`UiaFindAncestorByName(el, name, controlType := 0, …)`** walk UP from an element in hand (one parent step + one read a level; never `el` itself, never the desktop root): a window-wide `UiaFindById` on a big Chrome page regularly ran past a 400 ms timeout although the id was there, and walking up was instant. **Icon-font names**: a "…" toggle's accessible name was one private-use character (U+E611), so "has no name" checks failed — `UiaName(el, true)` / `UiaStripIcons` drop the Private Use Area (U+E000–U+F8FF and planes 15/16 — measured: AutoHotkey's PCRE runs in UTF mode, so a `\x{F0000}-\x{FFFFD}` range matches a whole surrogate pair, while a range of raw surrogates is a compile error) and trim; the default is unchanged. The tree dump shows such a character as `<U+E611>` (`UiaShowIcons`; `nameFilter` matches either form) while the **fingerprint still hashes the raw name**. **`UiaDumpSubtree(el, …)`** is the dump from any element (`UiaDumpTree` delegates to it; started at a window root it gives the window dump's fingerprint), and both take `positions` (` @x,y wxh`, ` @none`) and `visibleOnly` (a rectangle, not `IsOffscreen`, and inside every scroll container above it, its window and a monitor — `UiaVisibleRect`'s rule carried down the walk via `UiaClipAbove`/`UiaDumpChildClip` instead of re-climbing per node). Both are LINE options like `nameFilter`: which nodes are walked, the counts and the fingerprint are the same with them on or off (the suite pins it, with and without the line cap hit). They do add reads — `positions` one rectangle per printed line, `visibleOnly` a rectangle, `IsOffscreen` and the monitors per matching line plus a ScrollPattern check per node with children — and both stop once `maxLines` is reached (review, 2026-10-14: they ran for every node of the walk, roughly doubling a big page's cost). On a big browser page that can still push a walk into the 15 s time cap a plain dump finished inside (then `timeHit` and no fingerprint), so compare fingerprints between plain dumps. Icon characters: `UiaStripIcons`/`UiaShowIcons` scan code unit by code unit, so a lone surrogate (malformed UTF-16) is left alone — the first, regex-only version read a stray high surrogate plus the next real character as one plane-15/16 icon and dropped both (measured). The probe's tree mode takes them as trailing arguments — `["tree", window, max_depth, max_lines, name_filter, root_id, root_name, positions 0|1, visible_only 0|1]`, missing ones meaning the old behaviour; a requested root (both given = an element with both) adds a `root=<Type "name" <id=..>>` header line, and a root that can't be found is an `error=` answer carrying the find's reason.

**The function list is generated, not written** (2026-10-12, same session: "the UIA.ahk function list is only discoverable by reading the source") — `read_reference('uia')` / `read_reference('browser')` build the reference from this file and `lib\Browser.ahk` on every read (see `docs\architecture\mcp.md`), so **the comment directly above a function IS its reference entry**. Keep it that way: a public function's comment carries a line starting `Returns ` that says what it returns (`""`/`0`/`false`/an array/an object — the empty/failure value included — and what `&why` or any other `&out` holds), which the reference repeats as a `->` line right under the signature (`_returns_sentence`: from that line to the first line ending in `.`; feedback item 8 asked for return types, and several functions — `UiaFindById`, `UiaValue`'s empty case, `UiaIsPassword`'s false case — had never stated them; `test_library_functions_state_what_they_return` now fails on any public function without one); a section banner `; ---- name ----` becomes a heading; a vtable-slot table under a banner that says "vtable" is left out; a blank line between a comment and its function detaches the comment (it then shows as a loose note).

**Two rules for it, both learned the hard way.** (1) **Never point UIA at your own process** — querying a window belonging to the same script *hangs*, because UIA calls back into the provider on the thread already blocked inside the UIA call. It is timing-dependent: a small probe got away with it and the fuller test wedged permanently. There is no timeout and nothing to catch. **All three entrances now enforce this** (`UiaOtherProcess`, via `GetWindowThreadProcessId` — not `WinGetPID`, since control HWNDs go through here too): `UiaFromWindow` refuses an own-process window, `UiaFromPoint` refuses a point over one (`WindowFromPoint` pre-check), and `UiaFocused` refuses while one is foreground — each returns `""` instead of wedging. Every other window-scoped call funnels through `UiaFromWindow`. `tests\uia-selftest.ahk` asserts it, deliberately **last** — if the guard ever regresses that check hangs rather than fails, and the runner's 120 s kill is what turns it back into a reported failure. (2) It belongs in a module **body** (`hotkeys\bodies\`), which runs out of process — never `#Include`d into `VoiceKit.ahk`. That still holds: `VoiceKit.ahk` includes only `_Common.ahk` + `Theme.ahk` + `hotkeys\_index.ahk`, and the engine that now includes UIA (`lib\Workflow.ahk`) is not among them — workflow stubs, the Studio, NewAutomation and LoopRunner all run in their own processes. **The engine is no longer Acc-only** (see the engine bullet): it tries Acc first and falls back to UIA. The old note here said the engine deliberately stayed on Acc for one recording/playback path; current Chrome publishing no page content over MSAA made that untenable.

**`lib\Browser.ahk` — the browser-driving helpers** (2026-08-03) — the operational rules below, turned into code so nobody re-derives them per module. It `#Include`s `UIA.ahk` itself and follows the same out-of-process rule (body or `run_ahk_snippet` only, never the master). API: **`BrowserEnsureDomain(hwnd, fragment, timeoutMs)`** (read the omnibox; navigate and poll if the fragment isn't there — the "are you sure?" keystroke automation lacks, and what stops a query becoming a *Google* search. True proves the **omnibox**, not the page: a real Chromium shows the URL the moment Enter is pressed and keeps it on a can't-be-reached page — follow with a landmark `UiaTextPresent` when it matters), **`BrowserGrabPage(hwnd, minChars, timeoutMs)`** (select-all/copy, retried once after `{Esc}` when the result looks like a stranded-omnibox URL — `BrowserLooksLikeUrlOnly` is that test), **`BrowserUrl`** (`^l ^c {Esc}`, documented as the thing that must not precede a plain page grab), **`BrowserTypeVerified(hwnd, elementName, text)`** (find via `UiaFindEdit`, click for real, `{Esc}` the password-manager dropdown, select-all, type, then **read the FIELD back**), plus `BrowserActivate`/`BrowserSend`/`BrowserSendText`. Two design points: sends go out at **SendLevel 1** (invisible to a real browser, but it makes the helpers testable against an AHK "pretend browser" — the mechanism `press_hotkey` already uses), and **verification asks the element, not the keyboard** — `UiaValueOnly(el, &has)` (its trailing `&has` says whether a ValuePattern exists, so an EMPTY target field fails the check instead of falling back to copying whatever control has focus — 2026-09-30; new in `UIA.ahk`: ValuePattern with *no* Name fallback, since a check satisfiable by a label is not a check), falling back to select-all/copy only for controls with no ValuePattern. That was measured, not theorised: the clipboard-only version of the check reported success while the text had landed in a different control after an `{Esc}` moved focus. Names carry the `Browser`/`Uia` prefix deliberately — a bare `TypeVerified` in AHK's one shared namespace is a collision waiting to happen. `tests\browser-selftest.ahk` drives a **separate** pretend-browser process (`browser-selftest-target.ahk`) that emulates `^l`/`Esc`/`Enter` and can stage an unreachable site. §4.4's Tab-walk recipe stays documentation below — it is inherently site-specific.

**Driving a browser from a module body — hard-won rules** (2026-08-01, from a real scraping run against a public records site). These are operational, not code, and every one of them cost failed runs:
- **Never search-and-click a generic name** like "Close" over a whole window subtree — the browser's own window Close button matches, and you close the user's browser. Scope element names to page-unique strings. (`tests\engine-hybrid-selftest.ahk` *finds* "Minimize" to prove the UIA fallback works and pointedly does not click it.)
- **Browser password managers inject inline menus into web forms**, and an open menu eats Enter/Tab. Send `{Esc}` before typing and again before pressing Enter to submit.
- **Verify form input by reading it back** (select-all + copy, or `UiaValue` on the field) before submitting. Focus loss and stale field text are the two commonest silent failures and are invisible without a readback.
- **Detect a page by unique landmark text, not by field names.** A detail page can carry its own "Name:" label, so checking for "Name:" to mean "I'm on the search form" misfires during navigation gaps. The form's heading is the real landmark. `UiaTextPresent` is the tool for this.
- **`UiaFind` returns the label, not the input**, when they share a name — use `UiaFindEdit`. And for a form field, click it (`UiaClickCenter`) rather than Invoke it.
- **In a workflow, a form field is a `fill` step** (2026-09-30): it packages the rules above — input kinds only, a real click, a focus gate before any keystroke, a readback that tolerates reformatting but not a different value — and names duplicate labels with `#2`. No `{Esc}` there (see `docs\architecture\workflow-engine.md`); a module body driving a login form still wants the Esc rule above. When every box shares one name (a tax app's "expanded detail input"), the label is the **text before the box**: `after "Deductions" > "Insurance"` (2026-10-12) — one search from the window root, per the scoped-search rule above.

**Dry runs reach UIA too** (2026-10-12). `run_automation(dry_run=True)` replaces the input built-ins with `lib\DryRunShim.ahk`, which covers `UiaClickEl` (it clicks through `MouseClick`) and everything in `lib\Browser.ahk` (it types through `Send`/`SendText`). Three actions act through COM instead — `UiaSetValue`, `UiaInvoke`'s InvokePattern path and `UiaFocus` — so each asks `UiaDryRun(fn, el, text?)` first: true only when the shim's `_VkDryRunNote` exists (a by-name lookup that throws, caught, in every normal run — measured silent under `#Warn VarUnset`), in which case the action is logged and reported as done without happening. `UiaSetValue` still needs a ValuePattern to say true, as on a real run. `UiaScrollIntoView` is left live: it moves the view, not the data, and without it a virtualized element would have no rectangle for the (logged) click. That includes the rescue inside `UiaClickEl`'s pre-click checks, which also means a dry run refuses a hidden or covered target just as a real run does. A new UIA *action* — anything that changes the target app through COM — calls `UiaDryRun` the same way. Details: "Dry runs" in `docs\architecture\mcp.md`.
