The builder GUI and recorder, saving, the artifacts of a saved workflow, the recording options (browser tabs, maximize, pause capture, raw input, playback jitter) and the recorder's known limitations.

- `macros\WorkflowStudio.ahk` — builder GUI + recorder. Recording = window-switch polling timer + `#HotIf recording` mouse hotkeys + an `InputHook("V")` for keystrokes, with a floating always-on-top REC bar. **Conditionals in the Add dialog**: the four `if` variants + `else` + `endif` sit at the END of the Action dropdown (so they're never the default and don't clutter recording); a parallel `typeConds` array maps the four `if` rows to their condType (the on-disk type is just `if`). `RefreshLV` indents each row by `if`/`endif` depth so blocks read as nested. Recording never emits conditionals — they're authored only. **"Run a command and save its output"** (2026-09-30, the `capture` step) sits after "Set a value": edA = the name (no braces), edB = the command line, and the timeout goes in the **timeout box (`edT`)** and is stored in **paramC** — special-cased in `StepDialog`'s `UpdateFields`/`OK`/edit-prefill like `waitfor`'s seconds (blank = the engine's 30 s; a positive number otherwise). Authored only; the recorder never emits it. The step list shows the whole command (`WfDesc`: "Run <command> and save its output as {{name}}"), which is the review point for a shared workflow; the value hint's built-ins line says the selection names are "quoted for you" on `run`/`capture` rows. **Fill a field by its label** (2026-09-30): the `fill` row sits right after *Type text* in the Action list (`typeIds`/`typeConds`/`typeLabels`, one index); the dialog is window (Grab), the box's label (Pick element — point at the BOX; `#2` picks the second box with that label, `##` a literal `#`) and the value, which rides in paramC and so uses the third (`edT`) box, widened to 480 px for this row and back to 120 for the others. OK checks the label with the engine's own `WfFillLabel` and refuses a line break; the value is kept untrimmed and may be blank (clears the box). Authored only — the recorder never emits it. **Pick element falls back to UI Automation** (`PickNameAt`): MSAA first, as before, then `UiaName(UiaFromPoint())` when MSAA gives nothing, `Chrome Legacy Window` or the window title — so picking works inside a web page (a web form app's input screen) instead of reading the browser pane. For a `fill` step the picked name goes into the label box with every `#` doubled (`WfFillLabel` reads a trailing `#<digits>` as "the Nth box" and `##` as a literal `#`). Safe from the own-process hang (UiaFromPoint refuses a point over the Studio, which is hidden during the countdown anyway). The recorder's `CaptureTarget` is deliberately unchanged: it runs on button-down inside the click hotkey, where an extra cross-process lookup is felt.

**Pick a spot** (2026-07-27): the Add/Edit dialog's third capture button authors position-only pointer steps (click/dblclick/rclick/hover) — same 3-sec countdown as Pick element, but it captures the `ClassifyWindow` crit + window-relative `x,y` (the recorder's exact math) into the dialog's `preservedC`, so a hand-added step can target maps/canvases like a `CoordsOnly` recording; a dim caption shows the saved spot (also when editing a recorded click's fallback), element name still wins at playback when both are set, and the dialog's dim captions are passed to `ThemeShowModal` (lib\Theme.ahk — it replaced the Studio's `RunOwnedDialog`) because `ThemeApply` recolors every Text control (a bare `ThemeDim` before it is overwritten). Pressing **F9** (or Enter — Record is the `Default` button and gets focus on show) starts recording. **Command-line argument**: launched as `WorkflowStudio.ahk <file>`, `LoadStartupFile` loads a path under `workflows\` as that *named* workflow (Home's Edit button) and any other steps file as an *unsaved draft* (the AI draft from New Automation) — never auto-saving. `WorkflowStudio.ahk /record` instead starts recording immediately — used by `macros\RecordMySteps.ahk` ("open record my steps"), which is Studio-safe: a *visible* open Studio is activated and sent F9 (`SendLevel(1)` — the append-confirm guard still protects loaded steps), a *hidden* one (recording / mid-test) gets a TrayTip, and only when none exists is a fresh instance launched (a raw relaunch would kill the session via `#SingleInstance Force`). `RecordMySteps.ahk` is a **VoiceKit tool** (delete-protected in `_BUILTINS` and `_Common.ahk`'s `VkBuiltinTools`, listed in the tools section) and ships a **committed companion hotkey `Ctrl+Alt+Shift+W`** — so `hotkeys\RecordMySteps.hotkey.ahk` is tracked and its include + map line are in the shipped defaults (`hotkeys\_index.default.ahk`, `bridge-map.default.txt`) — the three must ship together, and `SeedUserFiles` adds the two lines to an upgraded install's live files (2026-09-30; the map header already exempts `.hotkey.ahk` lines from the Voice-Access recreate list, so W needs no manual pairing on a fresh install). Autosave recovery takes precedence over both argument forms: if the user accepts recovery, the argument is ignored (status line says so). `ClassifyWindow()` is the single decision point for what gets recorded and how windows are identified: Explorer folders → cleaned title + `ahk_class CabinetWClass` with an `explorer.exe "<path>"` relaunch command (path via `Shell.Application` COM); UWP apps → title + `ahk_exe ApplicationFrameHost.exe` (no relaunch command); everything else → `ahk_exe <name>.exe` + process path. Double-clicking a file in Explorer is rewritten into a `run|<full path>` step. The path comes from `ExplorerSelection` (and the relaunch folder from `ExplorerPath`), both one-line delegates to `lib\ExplorerSel.ahk` since 2026-09-30: the ACTIVE tab's single file-system item, so a double-click is no longer rewritten into a file from a background Windows 11 tab, and a virtual item (inside a `.zip`) stays a plain double-click.

**Saving is silent for a re-save** (2026-07-27): `SaveWorkflow(closeAfter := false)` prompts for a name (`SaveNameDialog`) and shows the phrase-teaching MsgBox **only when `currentPhrase = ""`** — a brand-new workflow, an AI draft, or recovered steps. A workflow that already has a name (loaded from the dropdown, from Home's Edit, or saved earlier this session) overwrites itself with no dialogs at all, reporting on the status line; the friction was killing the tweak-test-save loop. Consequence to know: **"save this under a different name" is no longer reachable** — the name dialog was the only duplicate-under-a-new-name path. Two guards on that name dialog (2026-09-30): a new name that's **already a saved workflow asks before replacing it** (`ConfirmReplaceDialog`, Cancel is the default; the existing file's exact spelling is kept so its phrase doesn't move), and **a VoiceKit tool's name is always refused**, caselessly (`VkDeleteProtected` — a stub under "New Automation" used to overwrite that tool's script; a legacy re-save under such a name clears the name so the next Save asks for another). The **Save and Close** button is the same call with `closeAfter := true` (hide, tray-confirm, `ExitApp` — recording is already stopped and the autosave cleared, so `CloseStudio`'s discard prompt has nothing to ask). Both buttons wire through `(*) =>` lambdas, since a Gui event handler's first positional arg is the control.

**A saved workflow is three artifacts** (plus one companion `.lnk`): `workflows\<Base>.steps.txt` (the single source of truth), `macros\<Base>.ahk` (a generated stub — text from `WfStubContent` in `Workflow.ahk` — that just calls `RunWorkflow`; contains the marker line "Generated by Workflow Studio" — `IsWorkflowStub` / `STUDIO_MARKER` — which save/delete check before overwriting or removing so hand-written macros are never clobbered; it was just "Workflow Studio" until 2026-09-30, which several tools merely mention), the Start Menu `.lnk` named by the spoken phrase, and a companion **`loop <phrase>.lnk`** (created by `MakeLoopShortcut`) that targets `lib\LoopRunner.ahk` with the base as its argument. The loop companion is created at save (WorkflowStudio `SaveWorkflow`) and on first-run/reinstall (`VoiceKit.ahk` iterates `workflows\*.steps.txt`), and removed on delete. Note the loop companion is a `.lnk` only — it does **not** change the byte-compared stub/steps formats, so it is outside the MCP conformance check; but the MCP writer creates it too (`make_loop_shortcut`) for feature parity, so keep both sides in sync. A workflow with `ask` steps may also own an optional **loop inputs sheet** (`workflows\<Base>.inputs.csv`, created on demand by the loop chooser — see the loop bullet) and, with `collect` steps, a **results overflow** (`workflows\<Base>.results.csv`, written only when the sheet was locked); both are user data, not generated formats, but delete flows must remove them.

Workflow Studio has a **"Close browser tabs before recording"** checkbox (`CloseBrowserTabs()`): when ticked, clicking Record first `WinClose`s every visible window of the common browsers so a recording starts from a clean browser. It is deliberately **graceful only** — a window still up after a few seconds is blocked by an unsaved-changes/"Leave site?" prompt, and it is left open and reported (never force-confirmed with a synthetic keystroke, which would silently discard the user's work). Its on/off state persists in `logs\settings.ini` (`[Studio] CloseBrowserTabs`).

**Recording foolproofing** (the 2026-07-09 pass): a second persisted checkbox, **"Maximize windows while recording"** (`[Studio] MaximizeWhileRecording`, default **on**) — `RecEnsureMax` maximizes each window that newly enters the take and records a `move|<win>|max` step so playback reproduces the geometry. Guardrails, all from an adversarial review — keep them: (1) **the click path must defer** — `RecClick` runs on button-DOWN, and a synchronous `WinMaximize` there reflows the window mid-gesture (breaks the user's live double-click; the Explorer rewrite can then record the *wrong file*), so clicks schedule `RecDeferredMax` via a one-shot timer of `GetDoubleClickTime()+150` ms (it re-checks `recording` and window existence); `RecTick` (focus-switch path) may call `RecEnsureMax` directly. (2) `recMaxed[crit]` is marked only AFTER the `WS_MAXIMIZEBOX` check passes — dialogs share their app's `ahk_exe` crit, and marking a dialog would permanently block the app's real main window that arrives later. (3) The captured element/coords of a window-entering click deliberately reflect pre-maximize geometry (recorded order: click, then move|max) — a *position-only* click that enters a window is therefore the one unprotected case; the ⚠ marker covers it and README says so. `RefreshLV` suffixes position-only clicks (element name empty, coords present) with ⚠, and `StopRecording` summarizes: zero-new-steps guidance, or a count of position-only clicks **in this take only** (`recStartCount` marks where the take began — counting the whole list would blame old steps on the new take).

**Pause capture** (2026-07-23: playback roughly matches the recording's pacing): `RecMarkPause` in WorkflowStudio.ahk pushes an ordinary `wait|<ms>` step (visible, editable, deletable — no format change, no toggle) right before a captured action whenever the gap since the last captured input reaches a floor: **700 ms before keyboard-bound steps** (`keys`, the first char of a typing burst, `ask`) vs **1500 ms before mouse/window steps** (clicks, hovers, `RecTick` focus switches) — floors differ because the engine already settles clicks/focus ~0.4–1.5 s but gives keystroke steps only their 150 ms beat. Values round to 100 ms and cap at **30 s** (a mid-recording distraction must not become a playback stall); the first action of a take never gets one (`recLastAct := 0` in StartRecording — that gap is the user getting ready). Invariants to keep: (1) the anchor `recLastAct` tracks **input events, never step pushes** — each typed char refreshes it, but `FlushTypedText` doesn't (the Type step lands long after the typing happened; the flush-*triggering* action then measures from the last char, which also puts the burst's own Wait in front of its Type step via the first-char check in `RecChar`), and the deferred `move|max` push doesn't touch it either. (2) The ask dialog's open time is excluded: the gap ends at the ^!+I press (`pressTick`), `RecMarkPause` runs before the anchor reset (it reads `recLastAct`), and the anchor resets when the dialog closes even on cancel. (3) The second press of a live double-click flows through `RecMarkPause` but sits under both floors, so a Wait can never split the pair. (4) Pauses *within* a typing burst don't split it — the buffer only flushes after `RecTick`'s 1.5 s idle, and a fresh burst then earns its own Wait. `StopRecording` counts in-take `wait` rows (they're all auto-captured) in the summary.

**Raw-input recording** (2026-07-27): a fourth persisted checkbox, **"Record raw input only"** (`[Studio] RawInput`, default off) — records nothing but the user's actual input, for bare key-sequence macros where the smart extras get in the way. One gate per feature: `RecMarkPause` early-returns (no auto `wait` steps anywhere — all seven call sites go through it), `RecTick` returns right after the typed-buffer idle flush (no window-switch `focus` steps; `recLastHwnd`/`recLastCrit` go stale but every reader of them is inside a raw-gated block), the focus-push in `RecClick`/`RecHover`/`RecAskInput`/`RecCollect` is skipped (`!chkRawInput.Value &&` on each), and `RecEnsureMax` no-ops (covers both the RecTick path and the deferred click/hover timers). Click/hover/drag capture itself is unchanged — element name per CoordsOnly, window crit + window-relative coords still recorded (a pointer step needs its window; the complaint raw mode answers is added *steps*, not window classification) — and the Explorer double-click→`run` rewrite stays, like CoordsOnly keeps it. The Maximize checkbox is disabled-but-value-preserved while raw is on (`SyncRawUI`, called from Load/SaveSettings — raw overrides it, and a grayed box says so). Playback of a raw take types/clicks into whatever window is active — deliberate, and the stop summary says so.

**Playback jitter** (2026-08-01): a fifth persisted checkbox, **"Vary click positions slightly when running"** — the only **playback** setting on that panel (every other box changes what gets *recorded*), which is why it is stored under `[Workflow] ClickJitter` and not `[Studio]`. The stored value is **pixels, not a flag**: the box is its on/off face, `LoadSettings` reads `> 0`, and `SaveSettings` writes back the existing number when re-ticking, so someone who put `6` in the file doesn't lose it by touching another checkbox. See the engine's "Pacing and aim" bullet for what it actually does.

## Recorder known limitations

- **Hovers are captured only on demand, not automatically.** The recorder hooks clicks and keystrokes, so passive mouse-rest can't be auto-detected; instead the user presses **Ctrl+Alt+Shift+H** while pointing at the target and `RecHover` records a `hover` step there (element name + window-relative coords, same capture as a click, respecting the position-only toggle). The engine's `hover` step MouseMoves there and dwells so the revealed menu/tooltip can be clicked by the next step. A hover can also be added by hand (Add → "Hover over …" → Pick element).
- **Ask-for-input is captured on demand too** — `Ctrl+Alt+Shift+I` while recording (`RecAskInput`): a themed dialog takes the label plus an optional **practice answer** (typing into the dialog is NOT recorded — `RecChar`/`RecKeyDown` ignore the Studio's own windows via `ClassifyWindow`), then an `ask` step is pushed (with a preceding `focus` if the active window is new to the take, so the answer lands in the right app) carrying the practice answer as its suggestion (paramB). If a practice answer was given, the recorder itself types it into the app (refocus + 300 ms settle + `SendText`) under the **`recSuppress` flag**, which `RecChar`/`RecKeyDown` early-return on — so the app gets real input to react to during recording, but no Type step is recorded and playback types only the asked answer at that spot (before this, the user's own sample typing became a Type step that replayed ON TOP of the ask answer, so the only safe move was leaving the field blank). `recSuppress` is cleared in a `finally` and reset by `StartRecording`; the anchor `recLastAct` is re-set after the auto-typing so it doesn't inflate the next captured pause. The hotkey itself is skipped in `RecKeyDown` like X and H.
- **Collect is captured on demand too** — `Ctrl+Alt+Shift+C` while recording (`RecCollect`): select the text FIRST (the selecting is itself recorded, so playback re-selects the same way), then the hotkey opens `CollectLabelDialog`, which **previews the current selection** — grabbed with `WfCopySelection` under `recSuppress` (KeyWait for the hotkey's modifiers to clear first), so the preview's own `^c` is never recorded and the clipboard survives. OK pushes `collect|<label>||` (with a preceding `focus` if the window is new to the take). The named-box variant is authored only (Add dialog: two `collect` dropdown rows disambiguated by a `typeConds` sentinel `"elem"` — NOT written to paramC, unlike `if`; the Pick-element guard keeps it from dumping a window crit into the label box). `^!+c` is skipped in `RecKeyDown` like X/H/I.
- **Drags ARE captured (2026-07-26); scrolling is not.** `RecClick` records every left press as a `click` step immediately (it can't know yet if a drag follows) and arms `recDragPend` (step index + press point + hwnd); the `~*LButton up` hotkey (`RecDragEnd`) rewrites that step in place into `drag|<window>||x1,y1,x2,y2` when the release point is ≥ 12 px away (past the 8 px double-click slop, under a one-word text selection). Both points are window-relative to the window's position at RELEASE time (one consistent frame). Guards to keep: the pend is cleared by the double-click upgrade path (the step is a `dblclick`/`run` by then), `RecDragEnd` verifies `steps[idx][1] = "click"` before rewriting, and a drag conversion resets `lastClick` so it can't be treated as half of a double-click. A drag is always positional (⚠ in the list, included in `RefreshLV`'s suffix check) but deliberately NOT counted in `StopRecording`'s position-only summary — that message blames unreadable element names, which doesn't apply. In the Add/Edit dialog the drag path is typed into the edB box but stored in paramC (special-cased in `StepDialog`'s OK + edit-prefill — the one exception to edB→paramB). Scrolling remains uncaptured.
- (Windows opening half-screen via snap layouts used to break takes — solved by the "Maximize windows while recording" option above.)
- **Position-only recording** — the Studio's third checkbox (`[Studio] CoordsOnly`, default off) makes `RecClick`/`RecHover` skip the Acc element-name capture and store just the window-relative `x,y`, for apps where accessible names are unreliable (maps, canvases, games). The Explorer double-click→`run|<path>` rewrite is deliberately kept (it's a reliable open-by-path, not a named click). Every such step is the ⚠ position-only kind; the stop summary acknowledges it's intentional rather than scolding.
