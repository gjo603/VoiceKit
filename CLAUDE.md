# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

VoiceKit is a Windows 11 voice-automation system: **Voice Access turns speech into triggers; AutoHotkey v2 does everything else.** There is no build system, package manager, or test framework — just AutoHotkey v2 scripts, pipe-delimited text data, and Start Menu shortcuts. Everything is AutoHotkey **v2 only**; most AHK code on the internet is v1 and will not run.

## Commands

AutoHotkey is at `C:\Program Files\AutoHotkey\v2\AutoHotkey64.exe`.

**Syntax-check a script** (the closest thing to a build). AutoHotkey is a GUI-subsystem exe, so `$LASTEXITCODE` after `&` is unreliable in PowerShell — use `Start-Process -Wait -PassThru` and read `.ExitCode`. Always pass `/ErrorStdOut`, otherwise load errors open a dialog and hang:

```powershell
$p = Start-Process "$env:ProgramFiles\AutoHotkey\v2\AutoHotkey64.exe" `
     -ArgumentList '/ErrorStdOut','/validate','"C:\Automations\VoiceKit\lib\Workflow.ahk"' `
     -Wait -PassThru -NoNewWindow -RedirectStandardOutput "$env:TEMP\ahkval.txt"
$p.ExitCode   # 0 = OK; error text is in the redirected stdout file
```

**Test the workflow engine end-to-end** (the established pattern — no framework): write a throwaway `.steps.txt` plus a harness script that calls `RunWorkflow()` and writes PASS/FAIL to a result file, then run it with a timeout. A timeout with no result file almost always means a step failed and its error MsgBox is blocking. Target throwaway AHK GUI windows with unique titles (e.g. a button that writes a proof file when clicked) — never drive the user's real windows in tests. **One more timeout cause**: PowerShell's `Start-Process -Wait` waits on the whole process TREE — a harness that reloads the resident master (e.g. testing hotkeys) never "finishes" because the master is its child. Check for the result file instead of trusting the wait, and never kill such a wrapper's tree without restarting `VoiceKit.ahk` afterward.

**Reload the resident master** after touching `hotkeys\`: run `VoiceKit.ahk` again (`#SingleInstance Force` replaces the instance) or press Ctrl+Alt+Shift+R.

**Never launch `macros\WorkflowStudio.ahk` as a smoke test without checking for a running instance** — `#SingleInstance Force` silently kills the user's open session and any unsaved recorded steps:

```powershell
Get-Process AutoHotkey64 -ErrorAction SilentlyContinue |
    Where-Object { $_.MainWindowTitle -like '*Workflow Studio*' }
```

## Architecture

**Two trigger paths** (see README for the user-facing story):

1. **Launch macros** — standalone scripts in `macros\`, each with a shortcut in Start Menu → `Voice Macros`. Voice Access natively opens Start Menu entries, so "open \<name\>" works with zero Voice Access config. This is why saving anything voice-triggerable means creating a `.lnk` there.
2. **Bridge hotkeys** — modules in `hotkeys\` bind `Ctrl+Alt+Shift+<key>`; the user manually pairs a Voice Access shortcut to that key combo (no API exists to do it programmatically — hard platform limit). `bridge-map.txt` is the registry of used keys and the user's recreate list. `_index.ahk` is the include manifest; `VoiceKit.ahk` (resident, tray icon) loads it. Reserved keys, excluded from the allocator pool (`BridgeKeyPool()` in `_Common.ahk`, mirrored by the writer's `BRIDGE_POOL`): **E, N, R** (master's own), **X** (Workflow Studio's stop-recording / loop-stop hotkey), **H** (Workflow Studio's mark-hover hotkey while recording — `^!+h` records a `hover` step at the mouse), **I** (its mark-ask-input hotkey while recording — `^!+i` opens a label dialog and records an `ask` step), and **C** (its mark-collect hotkey while recording — `^!+c` records a `collect` step for the current selection).

**The scaffolder** — `macros\NewAutomation.ahk` ("open new automation") is **intent-first and no-code-first**: a themed chooser of six plain-language intents, every flow a themed dialog (no `InputBox`/`MsgBox` chains). (1) **Open Something** generates a launch macro *inline* (a header + one `Run(...)` line via `AhkStrLit` — the string-literal escaper; `templates\launch-template.ahk` remains for the MCP writer and as documented building blocks). (2) **Record My Steps** goes through `OpenStudioSafely`, which **activates an existing Studio window instead of launching** (a raw launch's `#SingleInstance Force` would silently kill an open session). (3) **Type Text For Me** = snippet (one dialog, **multi-line** edit box; `SnipEncode`/`SnipDecode` in `_Common.ahk` are the shared escape codec — `SnipEncode` escapes backticks AND semicolons (a bare `;` would start a comment in the hotstring line) then folds real newlines into `` `n `` so a multi-line snippet stays on its single on-disk line, mirroring `voicekit_writer.create_snippet` exactly). (4) **AI Text Action** and (5) **Draft With AI** are the AI layer (below). (6) **Always-On Hotkey** offers no-code actions (open/type, generated inline) with "custom code" as the escape hatch (that path still uses `templates\hotkey-template.ahk` + Notepad); key allocation/`_index.ahk`/`bridge-map.txt`/reload unchanged, ending in a themed pairing-instructions dialog.

**The home window** — `macros\VoiceKitHome.ahk` ("open voice kit") lists every automation (workflows + their loop phrase, macros, AI actions, hotkey modules from `bridge-map.txt`, snippets parsed from `Snippets.ahk`, VoiceKit's own tools last) in a searchable ListView with Run / Edit / Hotkey / Delete / New Automation / AI Settings. Run for a hotkey row does `SendLevel(1)` + `Send` of the combo so hook hotkeys hear it. Edit for a workflow launches the Studio with the steps file as its argument (see Studio args below); Edit for a snippet opens an in-place editor (`EditSnippetDialog`: abbreviation + multi-line text, decoded with `SnipDecode`, rewritten with `ReplaceSnippetLine`, which preserves the line's position, its `:*:`/`::` options, and any comment above it — dynamic code-block snippets still open in Notepad); Delete removes *all* artifacts of an automation (for hotkeys: module file + `_index.ahk` line + `bridge-map.txt` line + master reload; tools can't be deleted). Its Start Menu entry is special-cased to **`Voice Kit.lnk`** (so the phrase is "open voice kit", not "open voice kit home") — both in `VoiceKit.ahk`'s first-run loop and in the window's own self-heal; this is the one exception to the SpaceOut naming convention. `macros\VoiceKitHelp.ahk` is now a thin alias that launches Home (keeps the old "open voice kit help" phrase working).

**Companion hotkeys** (2026-07-15: "also press Ctrl+Alt+Shift+\<key\>" for when voice is unavailable) — Home's **Hotkey** button gives any workflow / macro / AI action / tool a keyboard trigger (snippets are typed already; hotkey modules already have one). The helpers live in `lib\_Common.ahk`: `HotkeyCompanionCreate` writes `hotkeys\<Base>.hotkey.ahk` — **the `.hotkey.` filename suffix IS the marker** (safe: scaffolded names come from `CleanPhrase`, which strips dots) — generated self-contained (no `_Common` calls, missing-target TrayTip guard, runs `macros\<Base>.ahk` via `A_AhkPath`) so it standalone-`/validate`s, and the create **load-checks it BEFORE wiring** `_index.ahk` + `bridge-map.txt` (a broken module would take every hotkey down on reload); the caller reloads the master. Keys come from the same pool as the bridge allocator — `BridgeKeyPool()`/`BridgeFreeKeys()` in `_Common.ahk` are the AHK source of truth (`AllocateBridgeKey` and the writer's `BRIDGE_POOL` mirror it; `BridgeFreeKeys` deliberately raw-scans the map text, like the Python allocator, so commented-out lines still count as used). The convention has one owner per side: AHK `HotkeyCompanionRel`/`HotkeyCompanionParent`, Python `COMPANION_SUFFIX` + `_companion_rel`/`_companion_parent`; registry writes/reads go through `BridgeRegisterModule`/`BridgeMapEntries` (NewAutomation registers through it too; the writer mirrors with `get_bridge_map`). **Listings fold companions into their automation's row** (Home's Hotkey column; `list_automations`' `hotkey` field) — a companion line needs no Voice Access recreation (the map header + README say so) and must never appear as a hotkey row of its own; orphaned companions (automation deleted behind our back) surface in Home as deletable "(missing)" Hotkey rows. **Delete parity, three places**: Home's Delete, Studio's `DeleteWorkflow`, and MCP `delete_automation` (workflow/ai_action/launch_macro) all retire the companion — the AHK GUIs share `DeleteWorkflowArtifacts` (the whole five-artifact workflow-delete recipe) and `HotkeyCompanionRetire` (remove + reload-if-existed) in `_Common.ahk`. MCP `press_hotkey` can press companions (they're registered combos); *creating* one via MCP is deliberately unimplemented — GUI-only for now.

**The AI layer** (optional, opt-in — the deliberate exception to "no cloud calls") — `lib\AI.ahk` (OpenRouter chat-completions over `WinHttpRequest`, DPAPI-encrypted key + model in `logs\settings.ini` `[AI]`, `AISettingsDialog`, `AIComplete(system, user, &err)`, `AIGrabInput` clipboard-preserving selection grab) on top of `lib\Json.ahk` (minimal strict JSON parse/escape; objects→Map, arrays→Array, null→""). **Include order matters**: hosts must `#Include` `_Common.ahk` + `Theme.ahk` *before* `AI.ahk` (which includes `Json.ahk` itself). Nothing calls the network until a key is saved; the engine (`lib\Workflow.ahk`) has no AI knowledge. Three surfaces: **`macros\AskAI.ahk`** ("open ask ai" — Wispr-style bottom-center pill; answer is typed into the previously active window, else shown with Copy); **AI text actions** (`templates\ai-template.ahk` filled with `{{PHRASE}}/{{BASE}}/{{DATE}}`; the prompt lives in `prompts\<Base>.prompt.txt` so no code-escaping of user prompts is needed, and Home edits it in place); **Draft With AI** (New Automation: description → strict-JSON steps → `ParseDraft` validates types/if-conds/balance → writes `logs\ai-draft.steps.txt` via `WfEncode` → opens the Studio on it). **If step types ever change, `DraftSystemPrompt` + `ParseDraft` in NewAutomation.ahk join the three-way lockstep list** (engine / MCP writer / MCP schema) — a fourth place to update.

**The workflow subsystem** (one data format; engine + Acc + loop runner + builder):

- `lib\Workflow.ahk` — the engine. Parses and runs `workflows\<Base>.steps.txt`: one step per line, `type|paramA|paramB|paramC`, params percent-encoded (`WfEncode`/`WfDecode`; `%`, `|`, newlines). Step types: `run`, `focus` (activate-or-launch), `waitwin`, `wait`, `text`, `ask` (see below), `collect` (see below), `keys`, `click`/`dblclick`/`rclick`/`hover` (element-name first via Acc, recorded window-relative coords as fallback in paramC — `hover` MouseMoves there and dwells ~700 ms so hover-triggered menus/tooltips appear), `drag` (2026-07-26: `drag|<window>||x1,y1,x2,y2` — paramB stays empty, both window-relative press/release points live in paramC; playback presses, travels in ~16 small MouseMove increments — apps ignore a teleporting SendMode-Input move — and releases; always positional, so it goes through `WfPosOnlySettle` like a position-only click and gets the ⚠ marker; `WfDragDesc` renders the path and, like `WfDurDesc`, must never throw), `move`, `close`, plus the **branching** trio `if`/`else`/`endif`. The loader pads short lines, so older 3-field files still work. A failing step stops the run with an always-on-top MsgBox naming the step. **Playback is patient by design** (recorded timing is coarse, and pre-2026-07-23 recordings captured none — see pause capture below): a `focus` with no launch command and the click steps `WinWait` up to 10 s for their window before failing — don't "optimize" that back to an instant `WinExist` check. Position-only clicks/hovers (no element name) additionally go through `WfPosOnlySettle` — WinWaitActive + `WaitForInputIdle` on the window's process + a 1200 ms settle — because they fire blind and can't retry while content renders the way `AccFindByName`'s 3 s budget lets named clicks (a bare 400 ms pause clicked into half-loaded windows). **Abort hook** (2026-07-24): the global `wfRunAbortCheck` (a callable, "" when unset) makes a run stoppable mid-flight — `WfAborted()` is polled between steps, and every long block is sliced to honor it: `WfSleep` (Wait steps + the 300/400/700/1200 ms settles), `WfWinWait` (the 10 s window waits), `WfPosOnlySettle`'s WinWaitActive/WaitForInputIdle loops, and the ask dialog's wait (an open ask dialog is destroyed on abort). An aborted run returns false **quietly** — the failure MsgBox is suppressed when `WfAborted()` (a stop mid-window-wait must not pop "Window not found"), and the final `return !WfAborted()` covers a stop during the last step. The 150 ms beats and `AccFindByName`'s 3 s budget stay plain (sub-perceptible / Acc.ahk untouched). `RunWorkflowLoop` installs the hook (`(*) => wfLoopStop`) and clears it on exit, so Stop Looping cuts in mid-pass; non-loop runs never set it and are unaffected. `text` and `keys` steps end with a 150 ms settle (matching ask/click) — recorded keystroke steps otherwise replay back-to-back within milliseconds and race the app's UI (`{Down}` into an autocomplete list that hasn't populated). `WfDurDesc` renders wait milliseconds human-readably ("2.6 s") and must never throw — WfDesc draws the error popup for the very step whose param may be junk.
  - **Conditionals**: `RunWorkflowSteps` is an index/program-counter `while` loop (not a `for`-each), so an `if` whose condition is false can skip to its matching `else` (or past `endif`); `WfSkipToElseOrEndif`/`WfSkipToEndif` do depth-aware matching so blocks nest. An `if` step is `if|<window>|<element>|<condType>` — condType lives in **paramC** (like `click` keeps coords there), so the Studio's edA→paramA, edB→paramB field model is unchanged. `WfEvalCond` supports deterministic state tests only: `winexists`, `winnotexists`, `elementexists`, `elementnotexists`. Guardrails (from the production review): `WfEvalCond` rejects an **empty window** (else `WinExist("")` would match the last-found window and mis-branch); `WfElementPresent` uses a **short 700 ms Acc budget** (not the 3 s click-path budget) since a condition is a point-in-time snapshot — the long budget stalled every absent-element check, badly inside a loop. `else`/`endif` are param-less markers; unknown condType stops the run like a failed step. Balance is enforced at authoring time, not run time: Studio `BlockBalanceError` (and the MCP writer) refuse to save/test/create unbalanced `if`/`else`/`endif` — an unbalanced block would otherwise *silently truncate* the run while Test falsely reports success. Backward compatible: workflows with no `if` run identically (every step is a normal step).
  - **Ask-for-input** (2026-07-23): `ask|<label>|<suggested answer>|` collects a text value from the user and types it (SendText) at the step's position. **All asks are gathered UP FRONT**: `RunWorkflowSteps` calls `WfGatherInputs` before step 1 — one plain always-on-top dialog (`WfAskInputDialog`, native controls so Voice Access can click OK/Cancel; deliberately not themed — the engine keeps no Theme dependency) per **unique label** (case-insensitive; a repeated label is asked once, typed at every spot). Cancelling any dialog aborts the run **quietly** (returns false, no error popup). Asks inside an if-branch are still asked (branch outcomes aren't knowable up front — documented behavior). `RunWorkflowSteps(steps, askVals := "")` accepts a pre-filled Map to skip the dialogs — that's how the loop runner feeds batched rows. The `ask` case is handled inline in `RunWorkflowSteps` (like `if`/`else`/`endif`), NOT in `WfRunStep`. Blank labels fall back to "Input" via `WfAskLabel`, but every authoring surface (Studio dialog, MCP writer, ParseDraft) requires one.
  - **Collect / data collection** (2026-07-24): `collect|<label>|<element name>|` is ask's mirror — it GRABS a value at its position and saves it under the label. Empty element = **copy the current selection** (`WfCopySelection`: ClipboardAll save/restore, `^c`, 1 s ClipWait; nothing-copied is a step failure with a friendly message). Non-empty = **read that named box's accessible value** in the active window via `AccValueByName` (Acc.ahk grew `AccValue` + a node-returning `AccNodeOnce`; it PREFERS a same-named element with a non-empty value because oleacc gives a label and its box the same name — the label's empty value must not win; found-but-empty after the 3 s budget is a legitimate empty box, not a failure). Handled inline in `RunWorkflowSteps` (like `ask`), which takes a third param `collected` (a caseless Map the values land in; "" = discard). **Where values go**: the workflow's sheet, via `WfSheetApplyResults(sheetPath, askLabels, colLabels, results)` — each result `{src, ins, out}`: `src > 1` fills the collect columns of that sheet record (loop batches fed BY the sheet — `WfLoopCsvRows` tags each row Map with a `srcRec` *property*, and the chooser marks `plan.fromSheet`), `src = 0` appends a row of inputs-used + values-collected (single runs via `RunWorkflow`, which now pre-gathers inputs itself so it can save them; ask-each loop passes, imported/typed batches, input-less loops). Input columns precede collect columns; extra user columns/cells are preserved; a locked sheet (open in Excel — Excel locks CSVs) falls back to appending `<Base>.results.csv`, and nothing is ever overwritten that couldn't be read first. The CSV core (`WfCsvParse`, `WfCsvField`, `WfSheetWrite` — UTF-8 BOM + CRLF) moved INTO Workflow.ahk from WorkflowLoop.ahk so stubs get it. Studio **Test** passes a map and shows the values in a popup but never writes the sheet. `.inputs.csv`/`.results.csv` are delete artifacts (AHK `DeleteWorkflowArtifacts` + MCP delete).
- `lib\Acc.ahk` — minimal MSAA (oleacc) wrapper used for click-by-name. See the traps below before touching it.
- `lib\WorkflowLoop.ahk` + `lib\LoopRunner.ahk` — the **loop** feature. `RunWorkflowLoop(stepsFile, phrase)` (in WorkflowLoop.ahk) re-runs a workflow's steps until stopped, showing a themed always-on-top **Stop Looping** bar (bottom-left, work-area anchored), pausing `delayMs` (default 1500) between passes via an interruptible `WfLoopSleep`, and **stopping automatically if a step fails** (so a broken workflow can't spin). Stop = the voice-clickable button, or `Ctrl+Alt+Shift+X` (`WfLoopRequestStop` sets the `wfLoopStop` global) — and it's **immediate**: the loop installs the engine's `wfRunAbortCheck` hook (see the engine bullet), so a stop cuts in mid-pass, inside Wait steps and window-waits, with no failure popup. `LoopRunner.ahk` is the entry script the `loop <name>` shortcut targets — it reads the workflow base from `A_Args[1]`, resolves the steps file, and calls `RunWorkflowLoop`; `#SingleInstance Force` means only one loop runs at a time. WorkflowLoop.ahk requires Workflow.ahk + Theme.ahk to be included first (LoopRunner does this); it is **not** included by normal workflow stubs, so the engine keeps no Theme dependency. The stop hotkey reuses `Ctrl+Alt+Shift+X` (Studio's stop-recording key) — safe because looping and recording aren't concurrent; if both ever were, only one process wins the global-hotkey registration and the Stop button still works. **Batched loop inputs** (2026-07-23): if the workflow has `ask` steps, `RunWorkflowLoop` first shows `WfLoopInputPlan`, which leads with the workflow's **inputs sheet** — `workflows\<Base>.inputs.csv`, created on demand (`WfLoopSheetCreate`: header-only, one column per label, UTF-8 BOM + CRLF for Excel; `WfLoopCsvField` does RFC-4180 quoting) and opened via file association with a Notepad fallback; **Run from my sheet** re-reads it every time, a watcher timer (mtime+size stamp, fully try-guarded — it can fire between Destroy and the post-Show wait) refreshes the row count and moves the `Default` accent between the two sheet buttons, and the delete flows remove the sheet with the workflow (`DeleteWorkflowArtifacts` + MCP `delete_automation`). The dialog also sets the **pause between passes** (a seconds box; every start funnels through one `Start()` that validates it and persists per workflow to `logs\settings.ini` `[Loop] <Base>`; input-less loops keep the 1500 ms default and still start with no dialog). The other routes remain: import any **CSV** (picker), **type rows in** (`WfLoopTypeRows`, one edit per label + Add Row), or **ask each pass** — sheet and import share one validator, `WfLoopCsvRows` (header row must name every label case-insensitively, extra columns ignored, `WfCsvParse` is a real RFC-4180 parser: quoted fields may hold commas/doubled quotes/newlines; it now lives in Workflow.ahk). A batch runs one pass per row (`RunWorkflowSteps(steps, row, collected)` — no dialogs), shows "row i/n" on the bar, stops by itself after the last row, and reports completion; cancel aborts before the bar ever shows. **Collect write-back**: ask-each passes gather via `WfGatherInputs` in the LOOP (not the engine) so inputs can be saved beside results; each completed pass with collects pushes `{src, ins, out}` and the loop saves them all once at the end via `WfSheetApplyResults` (partial batches — stopped or failed midway — still save the completed rows; whenever a save succeeded, the loop ends with a YesNo "Open it now?" MsgBox — voice-clickable — that opens the saved file via `WfLoopOpenFile` (file association, Notepad fallback; `WfSheetApplyResults` returns the full `path` for this); a failed save still just TrayTips the error). **Headless batch** (2026-07-24): `RunWorkflowLoop(..., batchFile)` skips the chooser — the CSV is the batch, delay = the workflow's remembered pause, Stop bar still up; `LoopRunner.ahk <Base> <batch.csv>` is the entry (the MCP's `run_workflow_batch` writes `logs\mcp-batch.csv` and launches it; passing the sheet itself as batchFile sets fromSheet so results fill in place).
- `macros\WorkflowStudio.ahk` — builder GUI + recorder. Recording = window-switch polling timer + `#HotIf recording` mouse hotkeys + an `InputHook("V")` for keystrokes, with a floating always-on-top REC bar. **Conditionals in the Add dialog**: the four `if` variants + `else` + `endif` sit at the END of the Action dropdown (so they're never the default and don't clutter recording); a parallel `typeConds` array maps the four `if` rows to their condType (the on-disk type is just `if`). `RefreshLV` indents each row by `if`/`endif` depth so blocks read as nested. Recording never emits conditionals — they're authored only. Pressing **F9** (or Enter — Record is the `Default` button and gets focus on show) starts recording. **Command-line argument**: launched as `WorkflowStudio.ahk <file>`, `LoadStartupFile` loads a path under `workflows\` as that *named* workflow (Home's Edit button) and any other steps file as an *unsaved draft* (the AI draft from New Automation) — never auto-saving. `WorkflowStudio.ahk /record` instead starts recording immediately — used by `macros\RecordMySteps.ahk` ("open record my steps"), which is Studio-safe: a *visible* open Studio is activated and sent F9 (`SendLevel(1)` — the append-confirm guard still protects loaded steps), a *hidden* one (recording / mid-test) gets a TrayTip, and only when none exists is a fresh instance launched (a raw relaunch would kill the session via `#SingleInstance Force`). `RecordMySteps.ahk` is a **VoiceKit tool** (delete-protected in `_BUILTINS` and Home's `builtin` Map, listed in the tools section) and ships a **committed companion hotkey `Ctrl+Alt+Shift+W`** — so `hotkeys\RecordMySteps.hotkey.ahk`, its `_index.ahk` include, and its `bridge-map.txt` line are all tracked and must ship together (the map header already exempts `.hotkey.ahk` lines from the Voice-Access recreate list, so W needs no manual pairing on a fresh install). Autosave recovery takes precedence over both argument forms: if the user accepts recovery, the argument is ignored (status line says so). `ClassifyWindow()` is the single decision point for what gets recorded and how windows are identified: Explorer folders → cleaned title + `ahk_class CabinetWClass` with an `explorer.exe "<path>"` relaunch command (path via `Shell.Application` COM); UWP apps → title + `ahk_exe ApplicationFrameHost.exe` (no relaunch command); everything else → `ahk_exe <name>.exe` + process path. Double-clicking a file in Explorer is rewritten into a `run|<full path>` step.

**A saved workflow is three artifacts** (plus one companion `.lnk`): `workflows\<Base>.steps.txt` (the single source of truth), `macros\<Base>.ahk` (a generated stub that just calls `RunWorkflow`; contains the marker text "Workflow Studio", which save/delete checks before overwriting or removing so hand-written macros are never clobbered), the Start Menu `.lnk` named by the spoken phrase, and a companion **`loop <phrase>.lnk`** (created by `MakeLoopShortcut`) that targets `lib\LoopRunner.ahk` with the base as its argument. The loop companion is created at save (WorkflowStudio `SaveWorkflow`) and on first-run/reinstall (`VoiceKit.ahk` iterates `workflows\*.steps.txt`), and removed on delete. Note the loop companion is a `.lnk` only — it does **not** change the byte-compared stub/steps formats, so it is outside the MCP conformance check; but the MCP writer creates it too (`make_loop_shortcut`) for feature parity, so keep both sides in sync. A workflow with `ask` steps may also own an optional **loop inputs sheet** (`workflows\<Base>.inputs.csv`, created on demand by the loop chooser — see the loop bullet) and, with `collect` steps, a **results overflow** (`workflows\<Base>.results.csv`, written only when the sheet was locked); both are user data, not generated formats, but delete flows must remove them.

`lib\_Common.ahk` holds shared helpers (`EnsureDir`, `Notify`, `RunOrActivate`, `CleanPhrase`, `Log`, plus `RunAhk`/`MakeAhkShortcut`/`IsReservedName` — the last three make launching/shortcuts association-proof by targeting `A_AhkPath` with the script as an argument). Standalone macros include it via `#Include "%A_ScriptDir%\..\lib\_Common.ahk"`.

`lib\Theme.ahk` gives every GUI one modern look: it follows the Windows light/dark setting (`AppsUseLightTheme`), sets a matching title bar (DWM `DWMWA_USE_IMMERSIVE_DARK_MODE`), rounds corners (`ThemeRound`, DWM attribute 33 — matters for the caption-less floating bars), and dark-themes the **native** controls (`SetPreferredAppMode` ordinal 135 + `SetWindowTheme`, plus a `WM_CTLCOLOR*` hook for edit backgrounds). Call `ThemeApply(gui [, statusTextCtrl])` right before `Gui.Show()`; `ThemePalette()` returns the colors; `ThemeDim(ctrl)` colors a hint/caption; `ShowBottomLeft`/`ShowBottomCenter` place floating pills in the work area (center activates — it's for input bars like Ask AI). `VoiceKit.ahk` itself includes Theme now, for the first-run **welcome window** (Voice Access running-check with a turn-on button + live timer, start-at-login checkbox, "try saying" teach line — replaces the old MsgBox chain; the installed.flag is written *before* the welcome shows). **Keep controls native — never swap buttons for owner-drawn/custom widgets** — because Voice Access clicks a button by its accessible name (its caption); a custom widget has none. Button captions may carry a leading **monochrome, text-presentation** glyph (e.g. `●▶✕＋✎↑↓`, and `🖫` U+1F5AB for Save) but must keep the real word so voice matching still works; avoid emoji-presentation glyphs (`🗑💾⏺`) — they render in color and clash. Studio, New Automation, Home, Ask AI, AI Settings and the welcome window all call `ThemeApply` (Help is now a GUI-less alias).

Workflow Studio has a **"Close browser tabs before recording"** checkbox (`CloseBrowserTabs()`): when ticked, clicking Record first `WinClose`s every visible window of the common browsers so a recording starts from a clean browser. It is deliberately **graceful only** — a window still up after a few seconds is blocked by an unsaved-changes/"Leave site?" prompt, and it is left open and reported (never force-confirmed with a synthetic keystroke, which would silently discard the user's work). Its on/off state persists in `logs\settings.ini` (`[Studio] CloseBrowserTabs`).

**Recording foolproofing** (the 2026-07-09 pass): a second persisted checkbox, **"Maximize windows while recording"** (`[Studio] MaximizeWhileRecording`, default **on**) — `RecEnsureMax` maximizes each window that newly enters the take and records a `move|<win>|max` step so playback reproduces the geometry. Guardrails, all from an adversarial review — keep them: (1) **the click path must defer** — `RecClick` runs on button-DOWN, and a synchronous `WinMaximize` there reflows the window mid-gesture (breaks the user's live double-click; the Explorer rewrite can then record the *wrong file*), so clicks schedule `RecDeferredMax` via a one-shot timer of `GetDoubleClickTime()+150` ms (it re-checks `recording` and window existence); `RecTick` (focus-switch path) may call `RecEnsureMax` directly. (2) `recMaxed[crit]` is marked only AFTER the `WS_MAXIMIZEBOX` check passes — dialogs share their app's `ahk_exe` crit, and marking a dialog would permanently block the app's real main window that arrives later. (3) The captured element/coords of a window-entering click deliberately reflect pre-maximize geometry (recorded order: click, then move|max) — a *position-only* click that enters a window is therefore the one unprotected case; the ⚠ marker covers it and README says so. `RefreshLV` suffixes position-only clicks (element name empty, coords present) with ⚠, and `StopRecording` summarizes: zero-new-steps guidance, or a count of position-only clicks **in this take only** (`recStartCount` marks where the take began — counting the whole list would blame old steps on the new take).

**Pause capture** (2026-07-23: playback roughly matches the recording's pacing): `RecMarkPause` in WorkflowStudio.ahk pushes an ordinary `wait|<ms>` step (visible, editable, deletable — no format change, no toggle) right before a captured action whenever the gap since the last captured input reaches a floor: **700 ms before keyboard-bound steps** (`keys`, the first char of a typing burst, `ask`) vs **1500 ms before mouse/window steps** (clicks, hovers, `RecTick` focus switches) — floors differ because the engine already settles clicks/focus ~0.4–1.5 s but gives keystroke steps only their 150 ms beat. Values round to 100 ms and cap at **30 s** (a mid-recording distraction must not become a playback stall); the first action of a take never gets one (`recLastAct := 0` in StartRecording — that gap is the user getting ready). Invariants to keep: (1) the anchor `recLastAct` tracks **input events, never step pushes** — each typed char refreshes it, but `FlushTypedText` doesn't (the Type step lands long after the typing happened; the flush-*triggering* action then measures from the last char, which also puts the burst's own Wait in front of its Type step via the first-char check in `RecChar`), and the deferred `move|max` push doesn't touch it either. (2) The ask dialog's open time is excluded: the gap ends at the ^!+I press (`pressTick`), `RecMarkPause` runs before the anchor reset (it reads `recLastAct`), and the anchor resets when the dialog closes even on cancel. (3) The second press of a live double-click flows through `RecMarkPause` but sits under both floors, so a Wait can never split the pair. (4) Pauses *within* a typing burst don't split it — the buffer only flushes after `RecTick`'s 1.5 s idle, and a fresh burst then earns its own Wait. `StopRecording` counts in-take `wait` rows (they're all auto-captured) in the summary.

**Split Pages** (`macros\SplitPages.ahk` + `lib\split_pdf.py`) — a hand-written tool macro ("open split pages"): takes the PDF selected in File Explorer (topmost `CabinetWClass` window with a selection, via `Shell.Application`), splits it per page through the python helper (pypdf; a missing pypdf is a consented one-time `pip install`, recognized by the helper printing `NEEDS_PYPDF`), then cycles: preview in the default viewer → themed dialog for a short description → saved beside the original as `<yyyy-MM-dd> <description>.pdf` (collisions get ` (2)`; blank description falls back to `Page <n>`; Skip discards the page, Stop aborts the rest; the original is never touched). Test hook: `SplitPages.ahk <file.pdf> nopreview` bypasses Explorer lookup and the viewer.

**The MCP server** (`mcp\`, optional add-on — the repo's other Python besides `lib\split_pdf.py`) is a third automation path alongside the scaffolder and recorder: a FastMCP `server.py` exposing **create** tools (launch macros with a no-code `opens` mode, hotkey modules, snippets, workflows, AI actions + `update_ai_prompt`), **inspect** tools (`list_automations` mirrors the home window's categories with exact voice phrases, `read_workflow`, `get_bridge_map`), and **trigger** tools — `run_automation` (launches any spoken automation's macro; `loop <name>` phrases launch `lib\LoopRunner.ahk` with the workflow base; refuses to relaunch a running Workflow Studio — `#SingleInstance Force` would discard unsaved recorded steps; optional `wait_seconds` to report the outcome), `run_workflow_batch` (the "do X for each of these" tool: rows of label→value objects are validated against the workflow's ask labels, written to `logs\mcp-batch.csv` — Python `csv` module, utf-8-sig, same RFC-4180 dialect `WfCsvParse` reads — and `LoopRunner.ahk <Base> <batch>` runs them headlessly, one pass per row, Stop bar still up; collect values land in the sheet), `read_workflow_sheet` (parses `<Base>.inputs.csv` + `<Base>.results.csv` into columns/row-dicts so collected values flow back to the model — the read half of the batch round trip), and `press_hotkey` (synthesizes a bridge combo via a stdin-fed inline AHK script with `SendLevel 1`; validates the key is a single alphanumeric, refuses when the resident master isn't running, and can only press combos registered in `bridge-map.txt`, never arbitrary keys). Delete parity guards: dynamic code-block snippets are refused (line-delete would orphan the block and brick the master on reload — same rule as Home) with validate+rollback on the rewrite; workflow/hotkey deletes raise on nonexistent names and cross-guard same-named non-workflow macros; workflow/ai_action/launch_macro deletes also retire a companion hotkey (`_remove_companion_hotkey`) and `list_automations` folds companions into their automation's `hotkey` field, never listing `*.hotkey.ahk` as modules (see the companion-hotkeys paragraph above). `mcp\voicekit_writer.py` is a **deliberate second implementation** of the AHK write-side (`CleanPhrase`, `WfEncode`, `AhkStrLit`/the "Open Something" generator incl. its `;  Opens:` header line that Home parses, the `ai-template` fill + `prompts\` files, the bridge allocator, the stub/steps formats, **SpaceOut-named `.lnk` creation** and phrase-collision checks, the snippet brace/semicolon/duplicate guards, reload). Deletion protects VoiceKit's own tools **case-insensitively** (`_BUILTINS_LOWER` — spoken "Ask AI" cleans to base `AskAi`, and NTFS would match `AskAI.ahk`). This duplicates format knowledge that otherwise lives only in AHK — the tradeoff was accepted because `mcp\test_conformance.py` mechanically enforces parity: it feeds the writer's output through the **real** engine (`lib\Workflow.ahk` `WorkflowLoad`) and byte-compares, diffs a generated stub against a committed one, and covers the AI-action/opens/guard behaviors. **If you change any on-disk format (encoding, stub text, the `Workflow Studio` marker, file naming, BOM/LF), update `voicekit_writer.py` in lockstep and re-run the conformance test.** Newly created files are UTF-8 **with BOM** and **LF** endings (matching AHK `FileOpen`); the writer reproduces that exactly. Step-type coverage is a **three-way** lockstep — the AHK engine, `voicekit_writer.STEP_TYPES`, AND `server.py`'s `WorkflowStep` Pydantic `Literal` + `to_abc()` must all list the same types, or a type the engine supports becomes unreachable through MCP (this bit `if`/`else`/`endif` until the schema was extended; the writer also validates the `if` condType and `if/else/endif` balance at create time).

**Distribution** — committed tooling lives in **`build\`**; outputs go to **`dist\`** (gitignored). Run `build\Build-Installer.cmd` (double-click) or `build\Build-Installer.ps1 [-Exe]`: it stages **git-tracked files plus uncommitted edits to them** (`git stash create` + `git archive` — untracked personal automations never leak into a package, so **commit new source files before building**; a must-ship sanity list aborts the build if a core file is missing), drops the dev-only files (`build`, `CLAUDE.md`, `Setup.bat`, `.gitignore`, `.gitattributes`), bundles a portable `AutoHotkey64.exe` (so the tester needs no winget/AHK), adds `build\Install-VoiceKit.cmd`, and zips `dist\VoiceKit-Setup.zip`. `logs\` (which holds the DPAPI-wrapped OpenRouter key in `settings.ini`) and `prompts\` are gitignored, so they can neither be committed nor shipped. `Install-VoiceKit.cmd` robocopies to `%LOCALAPPDATA%\Programs\VoiceKit` and launches via the bundled interpreter (so `A_AhkPath`, and thus every generated macro/loop shortcut, uses the bundle). Production-review hardening baked into `build\Install-VoiceKit.cmd`: **excludes `Setup.bat`** (a wrong-file click would do a fragile in-place install pointing shortcuts at a temp folder), **`Unblock-File`s the target** to strip Mark-of-the-Web (the unsigned bundled exe would otherwise trip a security prompt; cancel = silent no-op install), and **scopes the pre-copy `taskkill`** to AutoHotkey processes whose path is under the target (a blanket `/im` would kill unrelated AHK scripts, but a `VoiceKit.ahk`-only filter would miss a running loop/Studio holding the file lock). `-Exe` wraps the zip into a self-extracting `.exe` via IExpress (`bootstrap.cmd` → delegates to the same installer) — IExpress needs an interactive desktop, so it no-ops headless.

## AutoHotkey v2 traps specific to this codebase

- **Functions and variables share one case-insensitive namespace.** `statusBar` exists because `sb` collides with `SB()`; don't name a variable `log` (`Log()` is defined in `_Common.ahk`, shadowing the math built-in) or reuse any function name as a variable.
- **`lib\Acc.ahk`: oleacc.dll must stay pinned** (`AccPin()` calls `LoadLibrary` once). AHK frees on-demand DLLs after each `DllCall`; the COM objects oleacc returns point back into the DLL image, so without the pin the first method call is a hard process crash (an unreadable vtable, no catchable error).
- **`accLocation` must be called through the raw vtable** (`ComCall(22, ComObjValue(acc), ...)` with a by-ref VARIANT) — IDispatch marshaling of its four `long*` out-params fails with "Type mismatch". Names/roles/children work fine through IDispatch.
- **Always pass `"UTF-8"` to `FileRead`** — the default ANSI read turns em-dashes in templates into mojibake (this bug shipped once already).
- **Dialog ownership**: the Studio window is AlwaysOnTop, so every MsgBox it opens must carry `"Owner" g.Hwnd` or it appears *behind* the Studio, unfocused. Prefer custom `Gui()` dialogs with `ThemeApply()` over `InputBox` so dialogs match the Studio's themed look (the save-name dialog already does this). Engine popups use the `262144` (always-on-top) MsgBox flag because they appear over arbitrary apps.
- **A modal dialog helper must capture the Gui's HWND into a local BEFORE `d.Show()`, then wait on the raw `"ahk_id " hwnd`** — never read `d.Hwnd` (or any property) again after Show. A voice click or a fast Enter on the `Default` button can destroy the Gui in the instant between `Show()` and the next line, and a property read on a destroyed Gui **throws "Gui has no window"** — which pops an error dialog and *hangs the whole run* (it surfaced as an intermittent ~50%-of-runs timeout in the ask-input engine test). `WinActivate`/`ControlFocus` also go in a `try` (the window may already be gone); `WinWaitClose` on an absent hwnd simply returns, so it's safe outside the try. This bit `RunOwnedDialog` (Add/Edit/Save) as well as the ask-input and loop-input dialogs — the fix pattern is `hwnd := d.Hwnd, edHwnd := ed.Hwnd` on the line above `d.Show()`.
- Steps are 4-element arrays (`[type, a, b, c]`) everywhere in memory; keep writes 4-field.
- Generated workflow stubs in `macros\` must never be hand-edited or treated as the source of truth — they are regenerated on every save; the steps file is canonical.
- **`lib\AI.ahk` include order**: hosts must include `_Common.ahk` and `Theme.ahk` *before* `AI.ahk` (it uses `EnsureDir`/`ThemeApply`/`ThemeDim` but deliberately doesn't include them — a second `#Include` via a different relative spelling risks duplicate definitions). `AI.ahk` pulls in `Json.ahk` itself.
- An AI action's prompt lives in `prompts\<Base>.prompt.txt`, NOT inside the generated macro — so user prompts never need AHK string-escaping and Home can edit them in place. Deleting an AI action must remove the prompt file too.


## Recorder known limitations

- **Hovers are captured only on demand, not automatically.** The recorder hooks clicks and keystrokes, so passive mouse-rest can't be auto-detected; instead the user presses **Ctrl+Alt+Shift+H** while pointing at the target and `RecHover` records a `hover` step there (element name + window-relative coords, same capture as a click, respecting the position-only toggle). The engine's `hover` step MouseMoves there and dwells so the revealed menu/tooltip can be clicked by the next step. A hover can also be added by hand (Add → "Hover over …" → Pick element).
- **Ask-for-input is captured on demand too** — `Ctrl+Alt+Shift+I` while recording (`RecAskInput`): a themed dialog takes the label plus an optional **practice answer** (typing into the dialog is NOT recorded — `RecChar`/`RecKeyDown` ignore the Studio's own windows via `ClassifyWindow`), then an `ask` step is pushed (with a preceding `focus` if the active window is new to the take, so the answer lands in the right app) carrying the practice answer as its suggestion (paramB). If a practice answer was given, the recorder itself types it into the app (refocus + 300 ms settle + `SendText`) under the **`recSuppress` flag**, which `RecChar`/`RecKeyDown` early-return on — so the app gets real input to react to during recording, but no Type step is recorded and playback types only the asked answer at that spot (before this, the user's own sample typing became a Type step that replayed ON TOP of the ask answer, so the only safe move was leaving the field blank). `recSuppress` is cleared in a `finally` and reset by `StartRecording`; the anchor `recLastAct` is re-set after the auto-typing so it doesn't inflate the next captured pause. The hotkey itself is skipped in `RecKeyDown` like X and H.
- **Collect is captured on demand too** — `Ctrl+Alt+Shift+C` while recording (`RecCollect`): select the text FIRST (the selecting is itself recorded, so playback re-selects the same way), then the hotkey opens `CollectLabelDialog`, which **previews the current selection** — grabbed with `WfCopySelection` under `recSuppress` (KeyWait for the hotkey's modifiers to clear first), so the preview's own `^c` is never recorded and the clipboard survives. OK pushes `collect|<label>||` (with a preceding `focus` if the window is new to the take). The named-box variant is authored only (Add dialog: two `collect` dropdown rows disambiguated by a `typeConds` sentinel `"elem"` — NOT written to paramC, unlike `if`; the Pick-element guard keeps it from dumping a window crit into the label box). `^!+c` is skipped in `RecKeyDown` like X/H/I.
- **Drags ARE captured (2026-07-26); scrolling is not.** `RecClick` records every left press as a `click` step immediately (it can't know yet if a drag follows) and arms `recDragPend` (step index + press point + hwnd); the `~*LButton up` hotkey (`RecDragEnd`) rewrites that step in place into `drag|<window>||x1,y1,x2,y2` when the release point is ≥ 12 px away (past the 8 px double-click slop, under a one-word text selection). Both points are window-relative to the window's position at RELEASE time (one consistent frame). Guards to keep: the pend is cleared by the double-click upgrade path (the step is a `dblclick`/`run` by then), `RecDragEnd` verifies `steps[idx][1] = "click"` before rewriting, and a drag conversion resets `lastClick` so it can't be treated as half of a double-click. A drag is always positional (⚠ in the list, included in `RefreshLV`'s suffix check) but deliberately NOT counted in `StopRecording`'s position-only summary — that message blames unreadable element names, which doesn't apply. In the Add/Edit dialog the drag path is typed into the edB box but stored in paramC (special-cased in `StepDialog`'s OK + edit-prefill — the one exception to edB→paramB). Scrolling remains uncaptured.
- (Windows opening half-screen via snap layouts used to break takes — solved by the "Maximize windows while recording" option above.)
- **Position-only recording** — the Studio's third checkbox (`[Studio] CoordsOnly`, default off) makes `RecClick`/`RecHover` skip the Acc element-name capture and store just the window-relative `x,y`, for apps where accessible names are unreliable (maps, canvases, games). The Explorer double-click→`run|<path>` rewrite is deliberately kept (it's a reliable open-by-path, not a named click). Every such step is the ⚠ position-only kind; the stop summary acknowledges it's intentional rather than scolding.

## UI conventions

- The **REC bar** floats at the **bottom-left** of the screen during recording, with a prominent **Stop Recording** button (bold, accent-bordered).
- The **Record My Steps** button in the New Automation chooser uses the `Default` (accent-bordered) style to stand out from the other choices.
- The **click** step type is labeled "Left-click" in the Add Step dialog to distinguish it from double-click and right-click.

## Design rules (from README — keep them)

- Voice Access shortcuts cannot be created programmatically; never promise otherwise. Anything voice-triggerable without manual setup must go through the Start Menu path.
- No raw coordinate-click automation as a primary mechanism (recorded clicks are element-name first; coordinates only as fallback), no pixel/image searching, nothing non-deterministic in the core. The OpenRouter/LLM integration the user floated **is now built** as the one sanctioned exception: strictly opt-in (dead until a key is saved), strictly additive (`lib\AI.ahk` + its three surfaces), and the deterministic engine (`lib\Workflow.ahk`) must never grow an AI step type or import.
